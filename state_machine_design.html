MAC System 状态流转与卡片设计

汇报卡片、流转卡片、质量确认卡片，以及人工中断处理

0. 三种卡片要分开

用户在微信/飞书里看到的不是“状态机”，而是三种不同职责的卡片：

卡片类型作用触发时机是否需要用户操作
汇报卡片展示本轮 Agent 干了什么、产出了什么、关键结论是什么Agent 执行完成，进入人工确认前只读
质量确认卡片让用户对本轮结果给出“通过 / 不通过”的明确意见汇报卡片之后必须操作（可默认通过）
状态流转卡片通知“状态变了”，比如“需求确认已完成 → 进入方案设计”状态发生 transition 后只读
现状问题： 目前只有“状态流转卡片”，把汇报和流转混在一起。用户看不到“本轮工作报告”，也没有机会对测试/Review 给出明确意见。

设计要点： 编码、测试、Review 都有质量确认，但只有 Agent 已明确判定 pass 时才允许按审批模式自动确认：

3. 条件自动确认怎么做？

有两种实现方式：

方案实现方式优点缺点
A. 状态机里仍用 human_confirmation，配置 auto_resolve approval_mode=auto 时，由 project_manager agent 自动选择“通过” 不改状态机，只改 approval_mode project_manager 也要调一次 LLM，有 token 成本
B. 状态机里拆分出 agent_execution + 可选的 human_confirmation 新增 CODING_CONFIRM_PENDING 等状态；正常模式走 human_confirmation，night/auto 模式直接 complete 跳过 完全可控，不调用额外 LLM 状态机变复杂
C. 现行：pass-only 条件自动确认 strict/normal 等待人工；night/auto 对 pass 立即 confirm；fail、REWORK、验收永不自动确认 失败不会被静默放行，行为由审批模式明确控制 需要持久化结果类型和中途输入检查
现行规则： 对编码、测试、Review 都产出独立汇报。只有明确 pass 且无 pending_user_inputs 时，night/auto 才自动确认；明确失败统一进入 REWORK，最终验收始终等待用户。

4. 状态机里考虑“人突然输入”了吗？

当前实现是事件驱动的：人来一条消息/命令，就处理一次。状态机本身没有“中断态”。下面是各种突发情况的行为：

用户行为当前行为问题建议
Agent 正在编码时发 /status 正常返回当前状态 无 保持
Agent 正在编码时发 /cancel 取消项目，kill 子进程 无 保持
Agent 正在编码时发 /confirm <id> 找不到 pending approval，回复“该审批已过期或不存在” 用户可能误操作 提示“当前没有待确认的审批，正在编码中，如需中断请用 /cancel”
Agent 正在编码时发任意自由文本 回复帮助信息 用户想追加需求/反馈却无法接入 识别为“追加反馈”，存入 pending_user_input，在下一轮确认/重试时注入
Agent 正在编码时发 /reject <id> 同 /confirm，可能找不到 approval 同上 同上，或允许强制进入 REWORK
人工确认阶段长时间不响应 一直 pending，等用户点击/命令 可能卡住 非关键节点（编码/测试/Review）加超时自动通过；关键节点（需求/方案/Spec/验收）继续等待
关键缺口： 当 Agent 正在运行时，用户除了 /status 和 /cancel 外，几乎无法对当前这一轮施加影响。建议引入 pending_user_input 机制：自由文本消息被暂存，Agent 本轮结束后先检查有没有 pending 输入，再决定是进入确认态还是直接进入 REWORK。

5. 建议的状态机变更

在 state_machines/feature.json 里增加这些状态：

新增状态类型事件
CODING_CONFIRM_PENDINGhuman_confirmationconfirm → TESTING；reject → REWORK
TESTING_CONFIRM_PENDINGhuman_confirmationconfirm → REVIEW；reject → REWORK
REVIEW_CONFIRM_PENDINGhuman_confirmationconfirm → ACCEPTANCE_PENDING；reject → REWORK
REWORKhuman_confirmationto_requirements / to_architecture / to_specs / to_coding

同时调整：

  • CODING 完成后进入 CODING_CONFIRM_PENDING，不再直接到 TESTING；
  • TESTING 完成后进入 TESTING_CONFIRM_PENDING；
  • REVIEW 完成后进入 REVIEW_CONFIRM_PENDING；
  • ACCEPTANCE_PENDING 的 reject 也进 REWORK，统一处理；
  • 质量确认只有 pass 结果可按 approval mode 自动 confirm；失败结果不可自动通过。

6. 总结

  • 汇报卡片 ≠ 状态流转卡片： 应该先有汇报卡片，再让用户确认，最后发流转通知。
  • 编码/测试/Review 都有质量确认： strict/normal 人工确认，night/auto 仅自动确认 pass。
  • 不通过统一进 REWORK： 由用户选择回到需求/方案/Spec/编码，而不是自动打回编码。
  • 上游文档需要变更确认： 回退到 PLANNING_* 后重新生成的文档，应该再经过一轮人工确认。
  • 突发输入需要处理： Agent 运行时用户的自由文本/命令应该被暂存为 pending_user_input，本轮结束后优先消费。
