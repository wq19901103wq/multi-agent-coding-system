关键设计：
  • 飞书是唯一外部入口；Admin 与 Control API 仅供运维/脚本，Control API 需要 Authorization: Bearer <CONTROL_API_TOKEN>。
  • lifespan 启动时扫描 stale running task、调用 recover_stale_tasks 标记失败、并通过 _resume_recovered_project 重新调度对应项目。
  • 所有 Runtime 调用使用 --setting-sources "" --bare，禁止 ~/.claude/settings.json 中的另一套 Kimi 端点污染项目运行时（详见 CURRENT_STATE Issue 3）。
  • SQLite 启用 WAL + 30s busy timeout + 外键检查；mac_system.db-shm/wal 已 gitignore。

3.2 关键事件语义

事件来源语义
completeAgent 输出 next_state_event=complete本轮完成，进入对应确认态
ask_userAgent 输出 question_batch主动提问，进入 *_INPUT_PENDING；回答后恢复原 execution 态
failOrchestrator 质量门判定失败规划/实现态 → FAILED；质量态 → REWORK
fail_max_retriesOrchestrator 检测超出重试上限质量态 → FAILED
runtime_exhaustedRuntime 技术重试耗尽进入 *_RECOVERY_PENDING，区别于质量 fail
confirm / reject用户点击确认卡confirm 推进；reject 规划态回到 $self、质量态进 REWORK
to_requirements/architecture/specs/coding/testing用户在 REWORK 卡选择回退层级跳到对应 execution 态
reject_to_requirements/architecture/specs验收驳回跳到对应规划态
审批模式与自动确认：
  • strict / normal：所有 human_confirmation 等待人工。
  • night / auto：同一 tick 内自动 confirm，但仅当 Agent 明确判定 pass 时。runtime failure、quality fail、REWORK、最终验收不得自动通过。

反馈与输入区分：
  • FeedbackPacket：Tester/Reviewer/验收 的结构化失败结论，按根因回退；下一轮 Agent 必须逐项报告处理结果。
  • PendingUserInput：Agent 运行期间用户发的自由文本/命令，被暂存；下一轮 tick 前消费，scope_change / correction 会强制质量关进入 REWORK。
  • QuestionInteraction + Question：Agent 主动提问的批量问题（unified ask_user），回答后恢复原 execution 态。
  • Approval：所有需要用户操作的人机节点都生成 Approval，approval_type=confirmation/input 区分确认/输入。

一个飞书聊天可关联多个项目；当前项目按"用户 × 聊天"隔离，避免跨项目串话。

  • 群聊：只处理 @机器人、命令、回复机器人消息和卡片动作；没有唯一当前项目时必须先选择。
  • 卡片路由：卡片和显式命令始终按其 project_id / approval_id 路由，不受后来切换影响。
  • 会话绑定 v2.2：/bind / /unbind 在 chat 有 active/paused 项目时拒绝；MAC_ALLOWED_BIND_ROOTS 限制可绑定目录。
  • 事件去重：ProcessedEvent + FeishuEventLog 按全局/重连水位线拒绝 stale 与乱序事件。
