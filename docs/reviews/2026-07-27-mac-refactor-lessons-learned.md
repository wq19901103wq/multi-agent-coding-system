# MAC 架构重构与黑盒验证复盘

> 日期：2026-07-27  
> 状态：已复盘，规则立即生效  
> 范围：Coordinator / Orchestrator、Agent 协作、状态机、飞书交互、生成项目边界与真实黑盒验收

## 1. 结论

这轮工作暴露的问题很多，而且并非单个 bug 造成。核心问题是：一开始没有把“MAC 是被测试和优化的系统、生成项目只是测试对象”贯彻到分析、开发和验收的每一步；同时把状态到达、结构化输出和自动化脚本成功，过早等同于真实用户任务成功。

因此出现了几类连续错误：

1. 权限和测试对象理解错误，曾把注意力放到直接完成生成项目，而不是验证 MAC 是否有能力完成它；
2. 黑盒测试不够真实，脚本和内部状态通过，但真实飞书私聊、卡片和用户可见结果仍失败；
3. Coordinator、Orchestrator、普通 Agent 和用户之间的职责边界不清，事实、问题、反馈和动作没有形成可靠闭环；
4. 验收证据缺少来源、范围和时效约束，导致系统把“无法验证”误判为“通过”；
5. 过度依赖 Prompt 自律，缺少确定性协议和 Handler 层保护；
6. 修复后验证只覆盖了预期路径，没有主动模拟真实用户的打断、改口、漏答、卡片重复、环境差异和恢复场景。

这不是“多修几个 Prompt”就能解决的问题。正确方向是：Prompt 负责推理，Schema 负责表达，确定性代码负责权限、状态和证据约束，真实黑盒负责最终裁决。

## 2. 我做错了什么

### 2.1 没有先固定测试对象与权限边界

最严重的错误，是一度把目标理解为“帮用户把个人网站做出来”，而实际目标是“只优化 MAC，通过提示词和 MAC 自身机制让它完成个人网站”。这导致早期方案偏离了测试目的，也让生成项目结果无法证明 MAC 的能力。

教训：开始任何跨仓库测试前，必须先写清楚三个对象：

- 被修改对象：MAC；
- 参考对象：例如 `mac-rpa`，只用于提取目标能力；
- 被交付对象：MAC 生成的项目，只能由 MAC 内部 Agent 修改。

如果这三个对象没有被明确区分，后面的成功结论都不可信。

### 2.2 把“系统能访问”误当成“Agent 应该读取”

Agent 具备读取 MAC 仓库文件的权限本身不一定有问题，但它读取了 MAC 的系统 Spec，并把与生成项目无关的内容带入任务。这说明只有文件系统权限边界，没有语义工作区边界。

我当时没有第一时间发现，是因为主要检查了“有没有越权写文件”和“流程有没有继续”，没有检查 Agent 实际读取了哪些内容、这些内容是否与当前项目相关。

教训：工作区隔离至少包含三层：

1. 文件权限：能不能访问；
2. 任务作用域：本任务允许访问哪些根目录；
3. 语义相关性：即使能访问，也只能读取与当前任务合同有关的内容。

测试时必须检查 Agent 工具轨迹中的读取目标，而不只是最终 diff。

### 2.3 把内部完成状态误当成用户任务完成

单元测试通过、E2E 脚本输出 `COMPLETED`、数据库进入终态，都不能独立证明真实交互正确。此前出现过流程完成但汇报卡片被吞、私聊回复不符合预期、Agent 重试过程不断向用户显示失败等情况。

教训：完成有四层，必须逐层成立：

1. 代码层：单元测试和合同校验通过；
2. 状态层：状态机正确到达预期状态；
3. 传输层：飞书消息和卡片真实发送、更新和响应成功；
4. 用户层：用户看到的内容、顺序、按钮和最终行为符合预期。

只有第四层能够裁决产品是否完成，前三层只是支持证据。

### 2.4 黑盒验证不够像真实用户

早期验证过多依赖 API、数据库和脚本 `expect`。这些手段适合快速定位，但不能替代用户从飞书私聊、手机浏览器或真实页面进行操作。

另外，桌面浏览器缩成手机宽度只能证明响应式布局，不能证明实体手机的局域网连通、浏览器兼容、触摸交互和真实网络环境。

教训：必须明确证据边界：

- 浏览器移动视口：只能证明布局和前端行为；
- 开发机访问局域网地址：只能证明服务端监听和本机网络路径；
- 实体手机访问并完成交互：才能证明手机端局域网验收项；
- 内部 Agent 的文字陈述：不能替代任何外部行为证据。

无法完成的外部验证必须保留为 pending，不能为了让流程结束而推断通过。

### 2.5 让 Coordinator 代答了不该代答的问题

新架构的方向是普通 Agent 只问 Coordinator，由 Coordinator 用已有事实回答，必要时再问用户。这个方向正确，但最初没有限制 Coordinator 可以回答什么，导致它用旧事实或不完整证据回答了必须由用户实际验证的验收问题。

教训：Coordinator 不是万能答案生成器。它只能回答满足以下条件的内容：

- 事实来源明确；
- 事实仍然有效；
- 事实范围与当前问题完全匹配；
- 该问题不要求用户主观选择、外部操作或敏感授权；
- 回答不会扩大项目范围或替用户作出验收结论。

手工验收、主观偏好、外部设备操作和授权类问题必须交给用户。

### 2.6 事实模型缺少来源、范围和时效

仅保存一段事实文本是不够的。同一句“已经验证”可能只代表桌面端、旧版本、另一项目或某个时间点。如果不记录来源、作用域和时间，Coordinator 很容易把过期或不相干事实提供给下游 Agent。

教训：事实至少需要：

- `value`：事实内容；
- `source`：用户、Agent、系统探针或外部服务；
- `scope`：项目、阶段、验收项、环境和适用 Agent；
- `created_at`：创建时间；
- `observed_at`：实际观察时间；
- `valid_until` 或失效规则；
- `confidence`：确定、推断或未验证；
- `supersedes`：替代了哪条旧事实。

时间戳不是装饰，而是判断事实能否继续使用的必要条件。

### 2.7 把 Prompt 当成了唯一约束

虽然 Prompt 中补充了 Schema 和 few-shot，但真实模型仍可能漏字段、混合多个问题、输出不兼容卡片结构或错误声明通过。只靠提示词要求“请严格遵守”无法形成可靠协议。

教训：

- Prompt 负责告诉 Agent 为什么以及如何做；
- Schema 负责限制可表达的结构；
- Runtime 负责拒绝不合规输出并提供精确重试反馈；
- Orchestrator/Handler 负责执行不可绕过的确定性规则；
- 测试负责证明错误输出确实被拒绝。

例如“每个手工验收项必须有独立问题且只有 `verified_pass` 能通过”，不能只写在 Prompt 中，必须由 Orchestrator 再校验和补齐。

### 2.8 澄清、问用户、反馈和动作没有彻底分开

早期设计把多种语义混在一起：Agent 缺信息、Coordinator 想确认理解、用户报告产品错误、用户修改验收证据，都可能落成相似的自由文本或卡片。结果是错误路由、重复提问，甚至把“只重跑验收”路由成重新编码。

教训：至少要区分：

- `resolution_request`：普通 Agent 请求 Coordinator 解决阻塞；
- `clarification_request`：Coordinator 需要补充事实才能继续推理；
- `ask_user`：Coordinator 决定必须由用户回答，并负责多轮追问；
- `feedback_packet`：对需求或交付结果的纠正，驱动 REWORK；
- `acceptance_evidence_update`：只修正验收证据并重跑验收；
- `approval`：用户对一个已形成结果作出确认或驳回；
- `action_request`：对系统执行动作的明确指令。

它们可以共享展示组件，但不能共享状态语义和路由逻辑。

### 2.9 用户打断和多轮对话设计不足

Coordinator 问了一个问题后，用户可能不回答，而是提出另一个问题、修改需求或讨论无关事项。若系统把下一条消息强行消费为问题答案，就会污染事实；若完全忽略原问题，又可能永久丢失阻塞。

教训：待回答问题必须有稳定身份和状态，用户新消息先由 Coordinator 判断：

- 是回答当前问题：绑定答案并继续；
- 是补充或纠正：更新事实后重新判断当前问题是否仍成立；
- 是新的项目问题：先回答新问题，再保留或更新原 pending 问题；
- 是明确取消或改范围：关闭旧问题并重算计划；
- 无法判断：用最小澄清追问，不擅自绑定。

问用户卡片和自然语言提问在产品层都是“Coordinator 向用户提问”，区别只在交互载体，不应形成两套业务语义。

### 2.10 对话结束后没有可靠地启动执行

Coordinator 有时能聊明白需求，却没有发出启动状态机所需的结构化动作。这说明“理解完成”与“执行开始”之间缺少明确合同。

教训：Coordinator 每轮输出不仅要有回复，还要有机器可执行的决策：

- 继续对话；
- 提问用户；
- 更新事实；
- 更新项目范围；
- 启动或恢复工作流；
- 路由反馈；
- 仅重跑某个质量阶段；
- 暂停或终止。

当启动条件已满足时，Handler 应消费明确动作并立即驱动状态机；不能依靠自然语言中“那我开始了”的隐含含义。

### 2.11 重复卡片本质是副作用幂等问题

重复卡片不只是模型重复说话。重试、恢复、重复事件、同一 tick 多次进入确认态以及发送成功后落库失败，都可能重复触发发送。

教训：任何外部副作用都必须有稳定幂等键：

```text
project_id + state_entry_id + card_purpose + page + round
```

发送前检查是否存在有效记录；发送成功后持久化消息 ID；恢复时优先更新原卡片而不是新发；旧审批在状态重入时必须过期。消息去重不能只依赖飞书 event ID，因为同一业务动作可能来自不同事件。

### 2.12 把自动重试暴露成了最终失败

用户在飞书看到连续“编码失败”“测试失败”，而后台其实仍在自动恢复。这会让系统显得不稳定，也让用户无法判断是否需要介入。

教训：必须区分：

- 本次调用无效，正在自动重试；
- Agent 合同违规，正在纠正；
- 阶段质量未通过，进入正常返工；
- 重试耗尽，真正需要用户处理。

前三者应更新同一进度消息或折叠展示，只有最后一种才发送最终失败卡片。恢复成功后必须让当前有效状态覆盖旧的临时失败表达。

### 2.13 飞书卡片能力做了未经真实验证的升级

自动使用 Card 2.0 内联表单与旧版选择结构组合，真实飞书接口返回 HTTP 400。单元测试只验证了生成 JSON，没有验证真实平台是否接受。

教训：外部协议的“结构看起来正确”不等于兼容。卡片升级必须：

1. 在隔离聊天中发送最小卡片；
2. 验证平台返回 200；
3. 真实点击并确认回调；
4. 验证重复点击和过期行为；
5. 再替换生产路径；
6. 保留稳定版本作为回退。

在没有真实验证前，应优先使用已知可靠的 Card 1.0 交互。

### 2.14 数据模型和运行代码发生漂移

审批过期逻辑给 `Approval` 写入不存在的 `updated_at` 字段。这类问题说明代码假设与模型定义没有一起演进，而且相关路径没有被测试覆盖。

教训：所有状态写入方法都必须有模型级测试；Schema、ORM 模型、迁移和业务代码要作为一个变更单元检查。不能因为 Python 允许动态赋值或某条路径平时少走，就假设字段存在。

### 2.15 异常被吞后，只看终态掩盖了真实缺陷

汇报卡片曾因 `page` / `total` 传入 `None` 抛出异常，但异常被吞，流程仍能继续，最终只剩确认卡片。E2E 因此显示成功，实际用户体验不完整。

教训：

- 可恢复异常可以不终止整个项目，但不能静默；
- 关键用户副作用失败必须进入结构化告警和测试断言；
- E2E 除状态终点外，还必须断言应出现的消息类型、数量和顺序；
- 跑完真实流程必须检查错误日志，不能只看脚本退出码。

### 2.16 测试用例过于相信实现者的预期

脚本测试容易只覆盖“代码认为用户会怎么操作”。真实用户会随机提问、漏答问题、突然改口、重复点击、在不同设备验证，或者只说“还是不对”。这些行为才暴露了路由和上下文缺陷。

教训：测试应同时包含：

- 白盒确定性单测；
- 状态机全分支测试；
- 真实飞书自动 E2E；
- 按用户历史行为抽象出的对抗用例；
- 用户明确要求时进行人工黑盒检查。

人工黑盒不必每次都做，但一旦用户指出脚本与实际不一致，本轮修复必须补做。

## 3. 架构上的最终认识

### 3.1 Coordinator 是唯一用户对话主体

普通 Agent 原则上只向 Coordinator 发出结构化解决请求。Coordinator 可以：

- 用有效事实直接回答；
- 调用 Orchestrator 查询项目状态或执行动作；
- 向其他内部能力查询；
- 判断必须询问用户；
- 在用户回答不完整时继续多轮推理。

`ask_user` 权限应收拢到 Coordinator。卡片和自然语言只是同一业务动作的不同 UI。

### 3.2 Orchestrator 是 Coordinator 的确定性工具

Orchestrator 不需要成为另一个面向用户的 Agent。它负责：

- 项目和状态机真相；
- Agent 调度；
- 审批、问题和反馈生命周期；
- 幂等与恢复；
- 确定性权限及质量门禁。

Coordinator 通过 Orchestrator 获得完整项目状态并执行决策。这样既保留多轮对话能力，也避免两个“总协调者”互相猜测状态。

### 3.3 下游 Agent 接收最小充分上下文

Coder、Tester、Reviewer 不应接收所有用户事实，也不应直接继承整段对话。Coordinator/Orchestrator 应根据任务合同提供：

- 当前阶段目标；
- 已确认需求与约束；
- 与该 Agent 有关的事实；
- 尚未关闭的结构化反馈；
- 可访问工作区；
- 输出 Schema 和 few-shot；
- 遇到阻塞时如何请求 Coordinator。

“最小充分”比“全部共享”更安全，也更能减少无关事实干扰。

### 3.4 事实、反馈、问题、审批必须可追踪

四者不能混成一段 `latest_feedback` 文本：

- 事实描述当前已知世界；
- 反馈描述某个结果为什么需要改变；
- 问题描述继续推理缺少什么；
- 审批描述用户对一个确定结果的决定。

每种对象都需要 ID、来源、作用域、时间、状态和关闭原因，状态重入时需要过期旧对象。

## 4. 今后的强制执行规则

### 4.1 开始前

1. 明确被修改系统、参考项目和生成项目；
2. 明确允许读、允许写和禁止操作的目录；
3. 写出用户入口和最终黑盒完成条件；
4. 区分自动验收项与必须人工完成的验收项；
5. 若存在不清晰的权限或目标，在修改前沟通。

### 4.2 实现时

1. 先定位通用根因，不为单句用户输入写硬编码；
2. Prompt、Schema、Runtime 校验和确定性 Policy 同步设计；
3. 任何状态变化和外部副作用都使用稳定 ID 与幂等键；
4. 事实必须记录来源、范围和时间；
5. 普通 Agent 的问题先交 Coordinator；
6. 只有 Coordinator 可以决定是否问用户；
7. 手工验收必须由对应的明确用户答案关闭；
8. 修验收证据不能自动变成重新编码；
9. 只修改 MAC，不直接修改生成项目。

### 4.3 测试时

1. 全量单测必须通过；
2. 真实飞书 E2E 必须覆盖 confirm、reject、select、rework、恢复和终态；
3. 检查真实卡片发送、点击、回调、重复点击和过期；
4. 检查用户看到的消息数量、顺序和失败语义；
5. 检查 Agent 读了哪些目录，而不仅是写了哪些文件；
6. 同一飞书聊天不并发运行多个 scenario；
7. 测试开关只通过进程环境临时设置，测试后恢复正常服务；
8. 不使用 `--reload`；
9. 检查最新服务日志中的卡片、类型错误和未处理异常；
10. 外部依赖或实体设备未验证时保持 pending，并如实报告。

### 4.4 宣称完成前

以下问题必须全部回答“是”：

- 真实用户入口是否通过，而不只是 API 通过？
- 用户看见的内容是否与内部状态一致？
- 所有手工验收项是否有对应用户证据？
- 是否存在被旧事实、另一环境或另一项目污染的结论？
- 是否直接修改过生成项目？若有，当前黑盒结论必须作废并重测；
- 是否检查了真实飞书卡片及日志？
- 是否恢复了正常服务配置？
- 是否仍有阻塞项被隐藏在“基本完成”中？

只要有一项为“否”，就不能宣称完整完成。

## 5. 本轮已经落地的改进

本轮已经将上述部分经验转化为系统能力和测试：

- Coordinator 成为普通 Agent 问题的统一处理入口；
- 对话决策可以启动、恢复、路由或仅重跑指定阶段；
- Schema 和 few-shot 进入各 Agent 的系统级合同；
- 手工验收按 AC 独立提问，只有明确 `verified_pass` 才能通过；
- Coordinator 不得代答外部设备和人工验收问题；
- 验收证据纠正可以原地重跑验收，不再错误调度 Coder；
- 问题卡回退到真实飞书验证过的稳定格式；
- 修复审批过期模型字段错误；
- 补充真实飞书全分支流程和相应回归测试；
- 验收评估缓存键纳入外部证据，新的用户结论会强制重新评估；
- 失效验收证据不会再被历史 QuestionInteraction 重新“复活”，证据账本一旦建立即为权威来源；
- 缺少或失效的人工验收证据会进入逐 AC 结构化补问，不再伪装成需要回退代码或 Spec；
- Coder 无交付文件变化时不再使验收证据失效；有实际修复时仅使反馈明确影响的 AC 失效；
- 辅助 Agent 执行期间对外显示 `running`，完成后才恢复 `waiting_user`；
- 个人网站通过真实飞书私聊与桌面浏览器完成正常对话、身份、记忆、加载态、故障提示、历史保留、恢复可用性和本地 URL 验证，并由 9/9 验收项推进至 `COMPLETED`。

最终验证结果（2026-07-28）：MAC 全量单元测试 `505 passed`；个人网站真实私聊黑盒项目 `proj_20260727_183128_b92f` 到达 `COMPLETED`；真实飞书 `full_feature_flow` 项目 `proj_20260728_010314_629b` 覆盖确认、驳回、选择、编码/测试/评审返工及验收驳回到需求后的全量重放，并到达 `COMPLETED`。该流程中两次 Planner 首次输出不符合 Schema（一次产物 `content_hash=null`，一次返回了产物描述而非 Agent 输出合同），MAC 均自动重试并成功恢复；这是模型非确定性被运行时合同拦截和恢复的实例，不应被误报为无失败发生。

### 5.1 多 Runtime 实测新增教训（2026-07-28）

- “CLI 能返回 JSON”不等于“CLI 能完成 Agent”：Codex 的无工具 smoke 成功，但首次真实架构任务调用文件工具时，未签名的 `code_mode_host` 被 macOS 拒绝，连续产生环境 blocker。Runtime contract test 必须至少执行一次真实工具。
- Coordinator 不能用自然语言承诺替代系统动作。对于 `preferred_resolver=runtime` 的 blocker，回答“已修复，请重试”并没有改变环境，只会形成内部澄清循环。RuntimeRouter 现在会真正切换 Provider；Codex 在 macOS 固定禁用故障 host，使用已验证的 shell tool。
- Provider 分配必须依据真实业务输出，而不是品牌或主观能力印象。Kimi Code 两轮都真实跑完 21 项测试并报告全部证据通过，却同时输出 `passed=false / fail`、`failures=[]`；转到有路径校验的 Project Manager 后，第一次真实飞书验证成功，紧接着复测又超过 120 秒无响应。最终 Kimi 保留为可配置 Runtime，但暂不承担任何默认生产角色。
- 多 Provider 的 JSONL 必须边读边推送脱敏工具摘要；先 `communicate()`、结束后统一解析虽然状态正确，但会让用户在长任务中看不到进度。
- 确定性系统能力不应包装成 Agent 任务。`/bind` 只是枚举允许根目录下一层的 Git 仓库，Claude 和 Kimi 都曾因自行扫描大目录超过交互等待上限；改为系统扫描后真实飞书即时返回。Agent 只保留在 `/create` 的语义命名环节，并有 45 秒超时与直接创建兜底。

多 Runtime 最终验证结果（2026-07-28）：全量单元测试 `511 passed`；真实飞书 `full_feature_flow` 项目 `proj_20260728_030155_5f9a` 以 Codex 承担 Architect/Coder、Claude 承担其余默认角色并到达 `COMPLETED`，71 条通知全部发送成功；`bind_dir_agent` 补测覆盖确定性 `/bind`、Project Manager `/create` 推荐、跳过绑定创建和自动清理测试项目。服务最终恢复为非测试模式，`18080` 正常监听、管理页返回 200、测试端点返回 404、飞书 WebSocket 已连接，且未使用 `--reload`。

### 5.2 主动验收与老仓库增量实测（2026-07-28）

- “人工验证方式”不等于“事实只能来自用户”。验收标准现在显式区分 `system_observable`、`user_preference`、`authorization` 和 `external_fact`；浏览器、HTTP、CLI、飞书及日志可观察行为必须由系统自己验证，不能因为描述写了“手工检查”就转嫁给用户。
- 新增只读 Codex `acceptance_agent` 主动启动和操作真实入口，再由 Claude `acceptance_evaluator` 独立复核。normal/night/auto 双重通过后直接交付，strict 才保留最终人工确认；只有偏好、授权或系统无法取得的外部事实可以打断用户。
- 黑盒必须覆盖已有目录，而不仅是新建空项目。`existing_repo_incremental` 真实创建带历史提交和旧文件的 Git 仓库，经飞书 `/bind` 后走完整交付链，并验证旧 README/legacy 内容保留、指定文件精确新增且仓库产生新提交。
- 重要信息必须先形成摘要层，不能让用户从技术事件中推断状态。飞书状态卡和 Admin 详情现在先展示工作目录类型、执行状态、等待原因、当前必要操作和完整执行链；底层 attempt、通知与事件仍保留供诊断，但不承担主叙事。
- 自动通过时“验收报告 + 状态流转”已经足够，额外发送“已自动确认”只是重复噪声；失败、阻塞或需外部事实时才在报告中逐项突出。

本轮真实结果：最终全量单测 `513 passed`。老仓库项目 `proj_20260728_044140_aa3a` 的 Codex 主动验收与 Claude 独立裁决均为 4/4 通过，20 条通知全部成功并自动到达 `COMPLETED`；全分支项目 `proj_20260728_045437_5d32` 覆盖需求/Spec 驳回、架构选择题、编码/测试/Review 分层 REWORK、strict 验收驳回到需求后的全量重放，两次主动验收与独立裁决均通过，71 条通知全部成功并到达 `COMPLETED`。期间一次 Planner Schema 漂移和一次 Provider socket 断开均由运行时自动恢复，没有要求用户介入。服务最终恢复为非测试模式，`18080` 正常监听、Admin 返回 200、测试端点在有效授权与有效请求体下返回 404、飞书 WebSocket 已连接，且未使用 `--reload`。

## 6. 仍需长期警惕的风险

即使本轮测试通过，以下风险不会因为一次修复永久消失：

- 模型升级后对 Schema、few-shot 和工具调用的遵循度变化；
- 飞书卡片协议或客户端行为变化；
- 历史事实逐渐失效却仍被复用；
- 状态恢复时重复发送外部副作用；
- 参考项目信息再次污染生成项目任务上下文；
- 自动化测试与真实手机、网络和用户行为产生偏差；
- 长流程中中间失败通知再次被误解为最终失败；
- 新增状态或对象后 ORM、Schema 和业务代码再次漂移。

这些风险应通过协议校验、可观测性、真实 E2E 和定期人工黑盒共同控制，不能重新退回“Prompt 写得更严一点就够了”的思路。

## 7. 最重要的经验

最重要的不是“以后少犯 bug”，而是建立一种不会轻易产生假成功的工作方式：

> 不把模型陈述当事实，不把内部状态当产品结果，不把脚本完成当用户完成，不把能够访问当应该访问，不把无法验证当默认通过，也不通过直接修生成项目来证明 MAC 有能力。

只有当 MAC 自己完成了工作，并且真实用户入口给出了与合同一致的可见结果，才算真正通过。
