# MAC 设计原则

## 1. 产品定位

MAC 是 Codex 原生 coding-agent 体验的飞书移动端、多后端扩展。用户可以像使用 Codex
或 Claude Code 一样连续提出新建、修改、调试和解释需求，同时获得更适合手机的选择卡、
进度卡和结果卡。

MAC 不把软件开发改造成审批流水线，也不要求用户管理 Agent。

## 2. 优先复用已验证实现

- 控制循环、上下文管理、工具调用和多 Agent 协议直接采用 Codex 已验证的实现。
- MAC 只实现产品确实需要、Codex 本身没有的适配层。
- 新增抽象前必须指出上游实现为什么不能满足；没有证据就不自行造轮子。
- 上游已有协议时，工具名、参数、状态和错误语义保持一致。

## 3. Root Agent 就是完整 coding agent

- 用户项目会话直接连接一个持久 Project Lead Thread。MAC 只依赖统一的 thread/turn 生命周期
  接口，当前默认由 Codex adapter 实现，不把 Codex 构造写进项目执行流程。
- Root Agent 能直接读写、运行、调试和验证项目，第一轮不降权。
- Root Agent 可使用 Codex 原生多 Agent 工具，但委派不是必经流程。
- 不存在额外的 Coordinator Agent、固定 worker/verifier 数量或专业 Agent 流水线。
- 子 Agent 是持久、可消息和可续接的 thread；是否创建由当前任务决定。

## 4. 动态工作，不预设流程

用户输入直接进入当前 Root Thread。Agent 根据当前代码和真实工具结果决定下一步。简单问题
可以直接回答，局部修改可以直接完成，多个独立任务可以并行委派。

Project Owner 不是前置协调器。所有普通消息直接进入 Root，不先按“简单/复杂”分类，也不固定执行一次
Owner 对齐。Root 可按需读取一份由 ProjectPolicy、生效用户策略和未完成决定投影出的精简结果契约；
当不同理解会改变用户可感知结果、授权、费用、外部事实或不可逆边界时，使用原生 request_user_input。
MAC 先展示原问题，再由隔离 Owner 核对用户历史：有充分依据就代答，没有依据才保留给用户。每轮完整
结果送达后 Owner 再独立审阅方向和未完成承诺。明确长期原则和至少两处独立真人来源支持的泛化原则
以带全部原话、时间及替代关系的 ProjectPolicy 持久化；具体命令和一次性选择只留在历史，执行汇报
不能覆盖，泛化原则不能代替用户授权。

禁止：

- 需求→架构→Spec→编码→测试→Review 的固定状态机；
- 根据关键词、错误文案或任务“复杂度”选择路径；
- R2/R3/R10 式无意义重复 Agent；
- 为单个失败案例增加硬编码兜底；
- 把测试输出和工具日志整包重放到下一轮 Prompt。

## 5. 最小充分上下文

- Root Thread 的历史、压缩和工具结果由 coding-agent 自己管理。
- Child Agent 的上下文使用 Codex 原生 `fork_turns` 语义。
- 外部后端只接收当前任务、必要事实、直接反馈和完成条件。
- 可能有用的历史经验、skills 和参考材料按需加载，不默认整包注入。
- 不在 MAC 中重复实现 coding-agent 的 compaction。旧 Thread 超过配置阈值时，只能调用 Codex
  官方原生压缩协议；项目、目录和 Thread identity 不变，失败也不得阻塞正常 turn。
- Prompt/KV Cache 以 provider、模型和会话为边界，不能跨 Codex、Claude、Kimi、Pi 搬运。
  简单任务由 Root 直接完成；相关的原生子任务优先续接已有 Child Thread；确需切换 provider 时
  只发送最小充分任务包，不能为追求“多 Agent”而重复支付完整上下文成本。
- 当前尝试失败或受阻时，真实失败信息先返回 Root。Root 判断阻塞是否会被所有 Agent 共享；只有
  独立 provider 可能提供新增价值时，才把必要事实、直接失败反馈和验收条件交给一个明确选择的
  Claude Code、Kimi 或 Pi。MAC runtime 不静默切换，也不串行尝试所有 provider。
- Project Owner 的例行汇报审阅先接收独立置顶的最新真人原话、解释指代所需的近期上下文、ProjectPolicy 和全部
  生效用户策略；执行证据默认只提供当前与最近 5 轮的用户要求、结果标题、状态和短摘要。旧 Owner 判断只作证据，不能继承为用户方向。每轮相同的
  偏好默认只带结论、范围、置信度和来源引用，跨项目真人选择默认只给最近
  5 条。完整汇报、偏好原始证据、更早选择、更早项目轮次和真人原始输入通过只读工具按需加载，不能
  读取源码或注入执行日志与完整 Root 对话。
- Project Owner 的最终决定使用 Codex 原生 turn-scoped 结构化输出一次返回；终态提交不得额外
  制造一轮只用于确认工具结果的模型调用。

## 6. 用户更少、更方便、更自由地输入

减少的是用户输入成本，不是系统输出：

- 用户只需表达想要的结果，不负责提前想到所有可能缺失的理念、方向、范围和验收口径；
- Root 发现会改变结果含义的未决事项时主动提问；Owner 先用历史权威代答，依据不足才给用户选择题；
- 多个相互依赖的问题由 Root 在同一原生 Turn 中逐步提出，已确认选择保留在原 Thread，不另建固定阶段；
- 用户可以随时用自然语言补充、纠正、切换话题或继续旧项目；
- 能做选择题时提供足以覆盖真实取舍的清晰选项，有推荐时排第一；
- 只有偏好、授权和系统无法取得的外部事实才需要用户回答；
- 未回答旧问题时，新消息仍通过原生 steer 进入同一 Root Turn，但不会被 MAC 猜成答案；原问题
  继续等待，用户的新消息本身就是最新事件，不回写旧问题卡；
- 普通内部决策和安全范围内的执行不要求用户审批。
- Root 确实需要用户输入时，隔离的 AI Project Owner 可基于用户已看见的结果卡和项目只读事实，
  代做有依据、低风险、可撤销的选择；偏好、授权、外部事实、凭证、费用和不可逆动作仍交给用户。
- Project Owner 可以跨项目、跨 session 读取同一用户明确提交过的选择和对 AI 决策的调整，把它们
  作为带项目与时间的偏好证据；同一判断至少在两个独立选择中重复出现后，才可形成可审计的推断偏好。
  用户在各 coding-agent 中亲自输入的完整原文和链接可进入只读历史档案供按需检索，但不默认注入；
  不得读取其他项目 Agent 输出或把一次性选择擅自泛化成永久偏好。
- 对命令、文件和额外权限的审批沿用 Codex 原生 `on-request` 协议。高把握的常规可撤销操作由
  Project Owner 代决；证据不足时原审批卡继续等待，不追加没有新判断的重复卡片。
- AI 代做的决定不打断用户，但必须完整留痕并允许调整；减少的是用户操作，不是知情权。原问题或
  审批卡先展示，Owner 代答后关闭旧交互，并在最新位置追加选择、依据和调整入口。
- 决策能力是旁路判断层。卡片按真实发生顺序记录事件；后来发生的提交、决定、审批结果和调整不得
  回写到时间线更早的卡片。旧交互无法撤回时保持历史内容不变，后台仍拒绝迟到回调。
- 每个成功或中断的用户可见终态展示后都由隔离的 Project Owner 审阅一次；provider 失败只收口并展示，
  不触发自动重试循环。原汇报卡显示审阅中和最终结论；Owner 作为用户代理主动判断最有价值的下一步，
  有把握时直接交给 Root 推动，需要用户确认时在最新位置给出明确意见和可操作建议/选择卡；每轮至少
  给出一条具体意见，不需要执行时明确建议保持现状、关注点或下一次最值得做的事。
- 每次审阅都保存结构化审计；无需执行的意见直接留在原汇报卡。建议卡必须至少
  提供一项可操作建议，存在真实取舍时提供实际互斥选项和推荐，不能重复汇报、制造空泛工作或自动启动执行。
- 决策卡默认只显示具体决定；事项、依据、影响和是否可调整使用与执行步骤相同的“···”原生折叠
  面板，Agent、模型、耗时和 Token 使用卡片下方统一的“Agent 与用量详情”。原生面板的展开只
  是本地视图状态；决定、调整和审批等业务状态仍必须与后台投影一致。
- 汇报审阅产生的决定如需继续执行，必须在决定所在结果卡或选择卡成功展示后交回原 Root Thread；纯验收或记录型
  决定只留痕，不额外启动一轮。

## 7. 输出充分但不暴露内部黑话

所有飞书交互使用卡片：

- 进度卡说明正在做什么和当前真实状态；
- 问题卡显示选择、已选答案和后台等待状态；
- 结果卡说明可见结果、验证和真实阻塞；
- 修改、打断或回答后，旧交互关闭，最新结果卡必须与后台一致；不得把后来发生的事实补写回旧卡。

默认不展示 thread id、task path、内部 stage/role、提交哈希、测试选择器、协议字段、
模型推理过程和原始日志；卡片标题必须使用用户能直接理解的动作或结果。
用户主动询问时才提供必要技术细节。

Project Owner 必须使用“普通人复述检查”：用户即使看不到代码、日志和 Agent 内部信息，也能一次读懂
要得到什么结果、为什么需要选择、选择后的差别。执行方提出的工具、部署、协议和排查办法不能被重新
包装成用户问题；系统能够自行修复、验证或回退的事项必须自行处理。结果卡和决策卡不得发布本机路径、
`localhost` 或 `127.0.0.1`；项目文件统一转换成签名的手机可访问链接，项目目录外的制品必须明确显示
尚未发布，不能伪装成可点击交付。

## 8. 一个状态一个事实来源

- Codex app-server event 是 turn 和原生 Child Agent 活动的事实来源；
- RootAgentSession 是项目 thread identity 的事实来源；
- QuestionInteraction/QuestionAnswer 是用户问题的事实来源；
- ProjectPolicy 只保存可指导未来判断的原则：用户明确长期表达的 `explicit`，或至少两处独立真人来源
  支持的 `inferred`；具体命令和一次性选择留在项目历史，`inferred` 不作为用户授权；
- UserOwnerMemory 是带范围、强度、用户原话证据和生效状态的长期用户策略来源；
- UserOwnerSource 是用户原始输入、链接与用户维护文档的只读证据档案，不是默认 Prompt 或偏好事实；
- ProjectDecision 是 AI 代用户决定、承诺及其调整历史的事实来源；
- NotificationOutbox/CardProjection 是通知和卡片投影的事实来源；
- Provider 原生 usage 加 MAC 外部后端账单是成本事实来源。

前端不自己维护另一套状态，Prompt 文本也不是状态数据库。

进度展示同样只描述可观察事实：已等待时间、最后一次真实活动、当前模型/工具/Child Agent
或外部 Provider。没有事件支撑时不显示百分比，也不能把“进程正常返回”写成“验收通过”。

## 9. 自主但不越权

Root Agent 可以完成当前项目范围内正常、可恢复的工程操作。只有以下事项升级给用户：

- 会改变产品方向的偏好；
- 新的敏感或外部授权；
- 系统无法观察的外部事实；
- 不可恢复或明显超出当前项目范围的动作。

私人本地项目不做脱离实际目标的企业级安全、分布式、迁移或治理设计。

Project Owner 不是第二个 Coordinator，也不是 Reviewer、Tester 或架构师。它是用户级代理，在 Codex 原生 `request_user_input` 边界
以及完整执行汇报成功展示后做一次隔离判断，不编码、不调度具体工具，也不进入 Root Thread。其
cwd 与项目隔离，输入只含已送达用户的结果/决策卡、当前可读问题或汇报、ProjectPolicy、相关用户策略、
未完成承诺、近期决定，以及显式白名单只读管理工具。它不读取源码，
技术正确性由 Root 动态委派独立 Reviewer、Tester 或 Verifier。它与执行 Agent 完全隔离；原问题、
审批和汇报卡始终先显示，后续 AI 选择或用户提交关闭旧交互并在最新位置追加，汇报决定在汇报后
追加到同一结果卡；需要用户选择时在最新位置追加选择卡。在用户意图、授权和边界明确时，它可以
决定下一方向并送回对应 Root 推动项目，但不能自己修改项目。

Owner 的长期能力来自结构化证据而不是隐藏常驻对话：项目内明确长期原则，或至少两处独立真人来源
共同支持的泛化原则保存在 ProjectPolicy；每条保存全部原文上下文并只能精确替代，具体命令和一次性
选择留在项目历史，执行汇报永远不能覆盖 ProjectPolicy；
未完成承诺和当前生效决定保存在决定账本；每个决定记录执行结果引用和完成/继续/阻塞状态；
用户跨项目偏好保存用户原话中可逐字举证的长期原则，以及至少两个独立选择共同支持的判断倾向；
每条带范围、强度、置信度、重复证据数、时间、来源 Project 和生效状态；
“在哪些项目生效”和“证据来自哪个项目”分别记录，不能因为策略是全局范围就丢失来源。
用户明确纠正旧策略时，只有精确引用被替换内容才会令旧记录失效。它用这些证据代答信息充分、
低风险、可撤销的问题和技术审批；缺少外部事实、新授权、真实费用或不可逆影响时仍交给用户。
历史导入遵循同一边界：可以扫描本机各 coding-agent 的真人 user 历史和用户维护的 Agent 指令文件，
但程序注入的任务 prompt、工具结果和项目专用合同不等于用户偏好；候选必须经独立 Owner 提炼、
与已有策略去重并保留逐字证据后才可写入。
Owner 不维护独立目标状态或定时复审。它的持久事实是 ProjectPolicy、ProjectHistoryRound、UserOwnerMemory、
决定账本和 ProjectOwnerReview；ProjectOwnerState 只保存项目级 Owner 开关，旧版快照列不再映射或写入。Owner 卡片
只展示当前结论和执行状态，依据、来源、记忆/规则变化及模型用量放在折叠区域。

结果卡送达后，Owner 审阅作为独立、持久、可恢复的后台任务运行，不继续占用项目执行锁；用户可以
立即开始下一轮。当前汇报只是待审查声明，不是项目事实。Owner 只校准当前请求及其明确未完成事项，
不从历史摘要推导新的工作方向。

只有来自用户的当前请求才是新增授权；Owner 触发的后续轮次和系统恢复文字必须显式标注来源，不能
被 Owner 再次当作用户授权。当前用户请求优先于旧决定和历史证据。状态查询、解释、只读检查和显式缩小范围的请求结束后，Owner
不得仅因为历史汇报提过后续方向就重启旧工作；任何继续执行都必须属于本轮请求及其明确未完成事项。
系统恢复只是续接同一轮的传输来源；后续 Owner 审阅仍使用该历史轮次原有的人类授权来源，但不继承旧
Owner 决定作为方向，不能因为服务重启把一轮真实用户请求降级为 `system_recovery`。

## 10. 黑盒优先验证产品能力

自动测试用于快速发现回归；真实飞书私聊和生成项目入口用于证明产品体验。对生成项目的修改
必须通过 MAC 完成，外部开发者不能直接替项目修代码。MAC 表现异常时可以检查 MAC 日志和
必要的生成项目证据，但修复必须发生在 MAC 层并覆盖同类问题。

T1–T9 的唯一含义见 `docs/testing-taxonomy.md`。任何报告都应逐层列出运行事实和未证明项，
不得用组件测试、注入接口或日志终态冒充真实飞书和生成项目黑盒。

## 11. 自由输入，结构化输出

MAC 的交互不是表单工作流。用户应当像使用 Codex 或 Claude Code 一样，随时直接输入需求、
问题、纠正、补充和新话题；slash command 和按钮只是可选快捷入口，不能成为完成工作的前置
条件。

系统主动产生的内容全部使用卡片：

- 需要用户决策时优先提供真实、清晰的互斥选项，有推荐时排第一，同时保留自由输入；
- 操作卡、问题卡和确认卡提交后必须原地显示已选结果或失效状态；
- 没有新时间线事件插入时，最新进度卡持续更新；出现真人消息、问题、审批或决定后轮换新卡，
  既避免无意义刷屏，也不跨时间回写旧卡；
- 结果卡完整说明结果、改动、验证、可访问产物和真实未完成项；
- 手机端减少的是操作成本，不是必要信息量。

## 12. 项目是唯一导航边界

用户可切换的长期工作边界是 Project。每个 Project 固定拥有一个工作目录和一个当前 Codex
Root Thread；Thread 内包含连续 Turn。目录不是独立的聊天状态，也不存在“已绑定但尚未成为
当前项目”的隐式中间态。

- `/create` 创建系统管理目录中的新项目并设为当前项目；
- `/open`（兼容 `/bind`）打开已有 Git 目录：优先恢复该用户在当前聊天已有的同目录项目，
  否则创建项目并立即设为当前项目；不同聊天使用独立 Project 和 Thread；
- `/use` 显式切换当前项目，目录和 Thread 随项目一起切换；
- `/new` 只为当前项目开始新的 Codex Thread，项目和目录保持不变；
- 普通消息只能进入明确选中的项目，禁止回退到“最近更新项目”；
- `/info` 展示当前项目自身的真实工作目录，不展示第二套目录绑定。

## 13. 进度卡是事件历史，不是固定流程

进度卡根据 Codex app-server 和外部 coding-agent 的真实事件动态形成层级，不预设需求、编码、
测试等固定阶段：

- 大步骤来自 Agent 的公开 commentary 或一次明确的外部 provider 委派；
- 已结束的大步骤保留摘要；
- 当前大步骤保留最近的小步骤历史，包括真实工具、文件、验证、Child Agent 和 provider 活动；
- 用户在运行中追加的要求也是新的时间线事件：展示层先冻结旧卡；native steer 成功后在最新位置
  新发当前进度卡并显示脱敏摘要，不另发独立的低信息量回执卡；native steer 被拒绝时转为下一
  Turn，旧卡同样不得再更新；
- 私有 reasoning 的生命周期消息不是步骤；每条小步骤必须包含用户可理解的真实活动，例如经过
  脱敏和截断的命令摘要、文件、工具名称或结果，而不是“开始/完成一轮分析”等协议翻译；
- 卡片按渐进披露组织：蓝色、绿色和红色分别表达运行、完成和失败，不再用正文重复状态；
  默认展开的“执行步骤”显示大步骤历史，运行中才显示当前步骤的小步骤；当前执行者、耗时和
  最近活动时间紧随其后；真实
  执行链、Agent 状态、模型、选择原因和分项用量放入下方默认折叠的详情面板。拿不到模型时
  明确写“后端未报告”，不能猜测；
- 超出手机首屏限制的步骤保留在可点击的“···”折叠区域；大步骤结束后只保留该大步骤，不再
  展示它已经完成的小步骤；
- 并行 Agent 必须显示为同一分支内的多个执行者及各自状态，不能渲染成虚假的串行顺序；详情
  可以显示公开 commentary、工具/文件/验证摘要和 provider 返回状态，但不能显示私有推理、
  内部 thread id 或 task path；
- provider 切换是步骤历史的一部分，不能被后续 Codex 活动覆盖后消失。
- 问题/审批出现后，旧进度卡冻结为历史。此时的新补充更新最新的问题/审批卡，并明确保留待答
  状态，不能为了显示新消息而跨越时间线去更新旧进度卡。
- Token 按 Codex Root、原生 Child Agent 和每个外部 provider 分项展示。缓存计数保留后端
  原始口径，区分输入子集与独立缓存读取；后端没有 usage 时明确写“后端未报告”，不得纳入
  可核验合计或推算成零。
