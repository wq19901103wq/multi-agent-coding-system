# MAC 测试与黑盒验证术语规范

> 状态：生效  
> 日期：2026-07-28  
> 目的：消除“单测、E2E、真实飞书、私聊黑盒、人工测试”等含混表达，确保开发者、Agent 和用户对验证范围有同一理解。

## 1. 总原则

不得单独使用“测试通过”“真实飞书 E2E”“黑盒通过”作为完成结论。每次报告至少要说清楚：

1. **被测对象**：MAC、飞书接入、状态机、生成项目，还是已有仓库增量流程；
2. **入口**：函数、API、测试端点、真实飞书群、真实飞书私聊界面、网站或 CLI；
3. **操作者**：FakeRuntime、脚本、Simulator Bot、桌面 UI 自动化、MAC 内部验收 Agent，还是用户本人；
4. **运行环境**：Fake Provider 还是真实 LLM，隔离测试库还是真实服务；
5. **证据边界**：是否查看了数据库、日志、源码和生成项目内部文件；
6. **通过范围**：本层证明了什么，以及明确不能证明什么。

“真实”只能修饰已经明确的部分。例如“经过真实飞书服务器传输”不等于“真实用户在私聊界面完成操作”。

## 2. 标准术语

### T1：单元测试（Unit Test）

- 入口：Python 函数、类或小范围模块；
- 操作者：pytest；
- Runtime：通常为 FakeRuntime、mock bridge、临时数据库；
- 证明：局部规则、Schema、状态转换和边界条件符合代码合同；
- 不能证明：真实 LLM、真实飞书传输、卡片渲染、私聊路由和用户可见体验。

示例：`pytest tests/test_orchestrator.py -q`。

### T2：集成/API 测试（Integration/API Test）

- 入口：FastAPI、SQLite、ProjectService、Orchestrator 等多个真实 MAC 模块；
- 操作者：pytest/TestClient 或本地 HTTP 客户端；
- Runtime：可以是 FakeRuntime；
- 证明：模块之间的数据写入、路由、幂等、恢复和 API 合同；
- 不能证明：真实飞书客户端和真实用户交互。

### T3：确定性流程模拟（Deterministic Workflow Simulation）

- 入口：状态机或 `test_full_flow.py`；
- 操作者：脚本；
- Runtime：FakeRuntime；
- 证明：confirm、reject、select、rework 等分支在确定性输入下能够走通；
- 不能证明：真实模型输出稳定性、真实平台传输和界面体验。

### T4：真实飞书传输 E2E（Feishu Transport E2E，简称 FRT-E2E）

- 入口：真实飞书服务器和 MAC WebSocket；
- 操作者：Simulator Bot；
- 会话：当前 `scripts/feishu_e2e.py` 主要使用真实飞书群；
- Runtime：真实 LLM；
- 允许：测试专用注入端点驱动卡片 action；
- 证明：真实飞书消息发送、群消息接收、卡片平台接受、回调、真实 LLM 和状态机能够协同；
- 不能证明：用户本人在私聊窗口输入、私聊上下文、桌面/手机渲染与点击体验。

以后不得把 T4 简写成“真实私聊测试”或“用户黑盒”。

### T5：真实私聊界面自动黑盒（P2P UI Black-box，简称 P2P-UI）

- 入口：用户可见的真实飞书私聊窗口；
- 操作者：桌面 UI 自动化，像用户一样点击聊天、输入并发送消息、点击可见卡片；
- 会话：`chat_type=p2p`，且消息出现在用户实际可查看的 Bot 私聊中；
- Runtime：真实服务和真实 LLM；
- 禁止用作交互替代：MAC API、测试注入端点、数据库写入、Simulator Bot 代发；
- 黑盒判定只使用：原始输入、可见回复、卡片、顺序、等待时间和截图；
- 诊断失败时可以另行查看 MAC 日志和数据库，但诊断证据不能反过来算作本轮 P2P-UI 通过。

用户所说的“在飞书私聊里自己模拟点击、输入、发送”专指 T5。

### T6：用户本人私聊黑盒（User P2P Black-box，简称 U-P2P）

- 入口：用户自己的手机或桌面飞书私聊；
- 操作者：用户本人；
- 证明：最接近实际使用环境的体验；
- 适用：用户主动抽测、主观偏好、实体设备或 UI 自动化无法可靠覆盖的行为。

T6 不是每次提交的默认要求；一旦用户明确反馈“T1-T5 通过但实际使用失败”，该轮不能再只用脚本结论关闭问题。

### T7：生成项目入口黑盒（Generated Project Black-box，简称 GP-BB）

- 入口：生成项目对用户公开的网站、CLI、App 或 API；
- 操作者：外部验证者、浏览器自动化或 MAC 的 Acceptance Agent；
- 黑盒期间禁止：查看生成项目源码、`.mac/` 产物、内部数据库和隐藏日志；
- 证明：生成项目的用户可见行为满足验收标准；
- 不能证明：MAC 的飞书私聊路由和 Coordinator 对话体验。

### T8：MAC 内部主动验收（Internal Active Acceptance，简称 IAA）

- 入口：生成项目公开入口；
- 操作者：MAC 内部只读 `acceptance_agent`，随后由 `acceptance_evaluator` 独立裁决；
- 证明：系统可观察的验收标准被主动验证；
- 不能证明：外部验收者没有权限访问的实体设备、账户状态、用户偏好，以及 MAC 私聊本身的体验。

IAA 属于系统交付能力，不等于 T5 或 T6。

### T9：诊断性白盒检查（Diagnostic White-box，简称 DIAG）

- 入口：MAC 日志、数据库、任务输出、Prompt、Schema；必要时最小只读查看生成项目；
- 目的：定位黑盒失败的根因；
- 规则：必须与黑盒回合分开记录；修复后重新从对应黑盒入口验证。

## 3. 场景名称与实际分类

| 场景或证据 | 正确分类 | 不得宣称 |
|---|---|---|
| `pytest tests/ -q` | T1 + T2 + 部分 T3 | 真实飞书或私聊通过 |
| `scripts/feishu_e2e.py --scenario full_feature_flow` | T4 FRT-E2E（真实群传输 + Simulator Bot + 真实 LLM） | T5 私聊 UI 黑盒 |
| `existing_repo_incremental` | T4 + 已有仓库完整性检查 + T8 | 私聊对话体验通过 |
| Codex `acceptance_agent` | T8 IAA | 用户本人验收或飞书私聊通过 |
| 浏览器验证 MAC Admin | Admin UI 黑盒 | 生成项目或飞书私聊通过 |
| 桌面操作真实 Bot 私聊窗口逐条发送问题 | T5 P2P-UI | 用户本人手机体验（T6） |

## 4. 什么时候必须跑哪一层

| 改动或问题 | 最低验证要求 |
|---|---|
| 纯函数、Schema、状态机规则 | T1；涉及跨模块时加 T2/T3 |
| Runtime、重试、Provider 路由 | T1/T2 + 真实 Runtime smoke；影响流程时加 T4 |
| 飞书卡片结构、发送、回调 | T1/T2 + T4 |
| Coordinator、自然语言问答、私聊上下文、记忆、重复回复、随机问题失败 | T1/T2 + **T5** |
| 用户明确报告私聊实际失败 | 修复后必须 T5；不能只用 T4 关闭 |
| 生成项目功能 | T8 + GP-BB；用户要求人工体验时加 T6 |
| 已有目录增量迭代 | T4/T5 中适用入口 + Git 历史和旧文件完整性检查 + T8/GP-BB |
| 宣称“本轮完整验证” | 所有与本次改动直接相关的层级均通过，并逐层列出 |

## 5. P2P-UI 的最低执行合同

一次有效的 T5 至少满足：

1. 从真实 Bot 私聊窗口开始，记录 `chat_type=p2p`；
2. 通过可见 UI 输入并发送，不调用发送 API 或注入端点；
3. 至少包含正常问答、连续多轮上下文、无关问题打断、必要澄清/选择题、错误恢复；
4. 如果目标涉及项目交付，继续覆盖项目创建、长 Agent 运行期间的状态查询、一次反馈修正和最终结果；
5. 记录每条原始输入、可见回复、消息顺序、耗时及失败截图；
6. 不用数据库状态或脚本 `COMPLETED` 替代可见结果；
7. 失败后先保存黑盒证据，再进入 T9；修复后使用新的消息回合重测；
8. 用户在自己的私聊中看不到这段交互，则不算 T5。
9. 完成新项目后，还要在同一真实入口覆盖已有项目迭代、需求修改、缺陷报告与 debug；不得用“新建另一个项目”代替老目录增量修改。
10. 对每张卡片核对信息密度：决策依据、当前阶段和必要操作必须可见；数据库 ID、状态机枚举、通用完成话术等内部噪声不得占据主界面。

### 5.1 T5 场景矩阵

“跑一次私聊项目”不等于完成 T5。一次完整体验审计应从下列场景中选择所有受本轮改动影响的行；项目生命周期或 Coordinator 改动默认至少覆盖前 8 行。

| 场景 | 必须观察的结果 |
|---|---|
| 普通问答 | 不创建项目，不要求用户替系统查内部事实 |
| 连续追问 | 能使用同一会话摘要与最近轮次，不重复回答 |
| Agent 运行中查询状态/成本 | 原任务不中断；回答来自项目快照及迭代链路 |
| 未回答澄清而改问别的问题 | 保留待澄清动作，先回答新问题，不重复发相同卡片 |
| 新项目完整交付 | 规划、编码、测试、评审、主动验收到终态均可见 |
| 已有项目功能迭代 | 复用原目录和基线合同，不退化为新建无关项目 |
| 已有项目修改需求 | 修订后的合同传到 Coder/Tester/Reviewer，旧合同不被静默丢弃 |
| 已有项目缺陷/debug | 可见问题形成结构化反馈，回退到正确阶段并完成回归 |
| Agent 运行中纠正 | 当前结果落地后自动消费纠正；同一条输入只执行一次 |
| 驳回与回退 | 反馈包指向对应阶段；不得靠错误文本关键词枚举失败类型 |
| Runtime/Schema 临时失败 | 内部重试不伪装成最终质量失败，不刷重复卡片 |
| 服务重启恢复 | 不重复启动 Agent，不把辅助 Agent 输出当作阶段结果 |
| 主动验收重试 | 环境问题可重新执行；累计 AC 集合必须精确覆盖 |
| 交付入口 | 只把当前可访问入口标成在线；临时端口停止后明确说明 |

每个场景记录“输入、可见输出、是否产生副作用、等待时间、判定”。失败后进入 T9 修复，再用不同措辞或相邻场景验证同类根因，不能只复测原句。

### 5.2 防止单 case 过拟合的验证合同

修复私聊问题必须同时满足：

1. 先给出跨措辞、跨项目仍成立的根因；
2. 自然语言只由 Coordinator/Agent 转换成结构化字段；Handler、Orchestrator 与权限层仅处理枚举、ID、状态、路径和授权；
3. 回归测试至少包含原场景、不同措辞的同类场景和一个容易被误伤的反例；
4. `tests/test_architecture_boundaries.py` 必须通过，它会扫描所有确定性路由边界中的关键词列表、同义词列表、自由文本 membership 和正则分类；
5. 若确实需要确定性解析，必须证明输入属于显式协议（命令、callback value、路径、Schema 字段），并在测试名中说明协议边界。

## 6. 测试报告模板

```text
本轮验证对象：

T1 单元测试：通过/失败/未运行；命令与数量
T2 集成/API：通过/失败/未运行；覆盖范围
T3 确定性流程：通过/失败/未运行；覆盖分支
T4 真实飞书传输 E2E：通过/失败/未运行；群/私聊、操作者、是否使用注入端点
T5 私聊 UI 自动黑盒：通过/失败/未运行；可见会话、输入集合、失败条目
T6 用户本人黑盒：由用户确认/未进行
T7 生成项目入口黑盒：通过/失败/未运行；入口
T8 MAC 内部主动验收：通过/失败/未运行；AC 数量
T9 诊断性白盒：是否发生；检查范围；不能计作黑盒通过

仍未证明的内容：
阻塞项：
```

## 7. 完成声明规则

- 只通过 T1-T3：只能说“自动化代码回归通过”。
- 通过 T4：只能说“真实飞书传输群 E2E 通过”，除非会话确实是 P2P-UI。
- 通过 T5：才可以说“真实飞书私聊 UI 自动黑盒通过”。
- T5 失败而 T4 通过时，整体私聊结论仍是失败。
- 任何未运行层级必须明确写“未运行”，不得省略造成已通过的暗示。
- “本轮完成”指所有适用层级均通过，不指某个脚本到达终态。
