# MAC 测试与黑盒验证术语

不得只说“测试通过”或“飞书 E2E 通过”。报告必须明确层级、入口、操作者、真实后端与尚未
证明的内容。

## T1–T9

| 层级 | 名称 | 入口与操作者 | 能证明 | 不能证明 |
|---|---|---|---|---|
| T1 | 单元测试 | pytest、单个模块、mock/Fake | 局部协议和边界 | 真实模型与 UI |
| T2 | 集成/API | FastAPI、SQLite、多个真实模块 | 路由、持久化、幂等 | 飞书客户端体验 |
| T3 | Root 协议模拟 | fake app-server JSON-RPC | thread/turn/request/event 适配 | 真实 Codex 行为 |
| T4 | 飞书传输 E2E | 真实飞书服务器、脚本/Simulator | 传输、回调、真实服务 | 真人私聊界面操作 |
| T5 | 私聊 UI 自动黑盒 | 桌面自动化点击真实 Bot 私聊 | 用户可见私聊体验 | 用户本人手机主观体验 |
| T6 | 用户本人黑盒 | 用户手机或桌面飞书 | 最接近实际使用 | 未覆盖的场景 |
| T7 | 生成项目入口黑盒 | 网站、CLI、App、API | 项目可见行为 | MAC 内部正确性 |
| T8 | MAC 内部主动验证 | Root/Child Agent 从真实入口验证 | 系统可观察结果 | 用户偏好和实体设备 |
| T9 | 诊断白盒 | MAC 日志、DB、事件；必要时只读目标项目 | 根因 | 不能计作黑盒通过 |

## T5 最低场景

涉及 Root Agent、私聊或项目生命周期的改动，至少覆盖：

1. 普通问题直接回答；
2. 同一项目连续追问；
3. 新建项目并完成一轮真实修改；
4. 已有项目继续迭代；
5. 提交一个可见缺陷并完成 debug；
6. Root 运行中追加纠正，验证 `turn/steer`；
7. 原生 `request_user_input` 选择和自由文本；
8. 未回答问题时提出另一问题；
9. 原生 Child Agent 启动、返回、打断的进度卡；
10. 服务重启后继续同一项目 thread；
11. 状态和成本查询；
12. 所有可见输出均为卡片且不泄露内部黑话。

每个场景记录：原始输入、可见输出、等待时间、是否产生副作用、通过/失败和截图。失败后先
保留黑盒证据，再进入 T9；修复后用相邻措辞和相邻场景重测，不能只复测原句。

## 个人 Agent 项目验证

这是 T5 + T7，不得用源码检查代替：

- 通过真实飞书私聊让 MAC 修改目标项目；
- 通过真实网页检查身份、语气、人物记忆、跨轮记忆、few-shot、skills 和工具；
- 验证发送文件；
- 验证移动端界面与页面稳定访问；
- 重启 MAC 和目标服务后复测；
- 外部开发者不直接修改目标项目。

## 报告模板

```text
被测对象：
代码版本 / 服务版本：

T1：通过 / 失败 / 未运行；命令、数量
T2：通过 / 失败 / 未运行；覆盖范围
T3：通过 / 失败 / 未运行；协议场景
T4：通过 / 失败 / 未运行；会话、操作者、是否使用注入端点
T5：通过 / 失败 / 未运行；真实私聊输入与可见结果
T6：用户确认 / 未进行
T7：通过 / 失败 / 未运行；入口和场景
T8：通过 / 失败 / 未运行；真实验证
T9：是否发生；检查范围（不计作黑盒通过）

仍未证明：
阻塞：
```

## 完成声明

- 只有 T1–T3：只能说自动代码回归通过。
- 通过 T4：只能说真实飞书传输通过。
- 通过 T5：才可以说真实飞书私聊 UI 自动黑盒通过。
- T5 失败时，T1–T4 通过也不能关闭私聊问题。
- 项目功能必须有 T7；MAC 内部自验必须单独标为 T8。
- 所有适用层级通过后才能说本轮完成。
