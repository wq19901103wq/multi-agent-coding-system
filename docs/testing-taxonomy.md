# MAC 测试与黑盒验证术语

不得只说“测试通过”或“飞书 E2E 通过”。报告必须明确测试层级、入口、是否使用真实服务与
真实 Provider，以及尚未证明的内容。脚本显示 completed、FakeRuntime 和测试注入接口都
不能代替真实飞书界面黑盒。

## T1–T9 唯一口径

| 层级 | 名称 | 入口与操作者 | 主要证明内容 |
|---|---|---|---|
| T1 | 静态边界检查 | 编译、导入、架构禁止项扫描 | 代码可加载且没有重新引入禁止架构 |
| T2 | 单元测试 | 纯函数、模型、小组件，允许 mock/Fake | 局部逻辑和协议边界 |
| T3 | 组件集成测试 | SQLite、app-server 协议、outbox、卡片动作 | 多组件持久化、幂等和投影一致性 |
| T4 | 本机 API/进程测试 | 真实服务、健康检查、自动 E2E、重启恢复 | 本机运行、协议传输和进程生命周期 |
| T5 | 真实飞书私聊界面黑盒 | 已登录飞书 UI 中点击、输入、查看卡片 | 用户实际可见的移动端/桌面私聊体验 |
| T6 | 真实外部模型/Provider 测试 | Codex、Claude Code、Kimi、Pi 等真实后端 | 外部执行、失败语义、计量和选择证据 |
| T7 | 完整新项目交付黑盒 | 从真实飞书新建项目直至可运行验收 | MAC 能完成新项目端到端交付 |
| T8 | 已有目录迭代/修改/debug 黑盒 | `/bind` 绑定真实旧目录后从飞书操作 | MAC 能安全连续维护已有项目 |
| T9 | 生成项目运行验收 | 真实网页、API、文件能力和重启后的可用性 | 生成项目对最终用户真的可用且稳定 |

日志、数据库、事件和必要的目标项目只读检查属于诊断手段，不单独计作一个测试层级，也不能
替代 T5–T9。发现异常时应先保留黑盒证据，再用这些手段定位共同根因；修复后必须回到原入口
并使用相邻措辞或相邻场景重测，不能只复测一个原句。

## T5 最低场景

涉及 Root Agent、私聊或项目生命周期的改动，至少覆盖：

1. 新项目首次请求和普通问题直接回答；
2. 同项目多轮迭代；
3. Root 运行中追加纠正，验证 `turn/steer`；
4. 原生 `request_user_input` 选择、提交、卡片回执及同 turn 续接；
5. 未回答问题时提出另一个问题；
6. 项目切换和 session 隔离；
7. 已有目录修改和 debug；
8. 服务重启后恢复 thread；
9. 原生 Child Agent 状态和外部 Provider 真实活动；
10. 失败信息可见且没有重复卡片；
11. 状态和成本查询；
12. 所有用户可见输出均为卡片，不泄露内部黑话。

同一聊天窗口不得并发执行多个黑盒场景。每个场景记录原始输入、可见输出、关键等待时间、
副作用、通过/失败和必要截图。

## 个人 Agent 项目验证

个人 Agent 同时需要 T5、T8 和 T9，不能用源码检查代替：

- 通过真实飞书私聊让 MAC 迭代已有目标目录；
- 通过真实网页输入框检查身份、语气、人物记忆、跨轮记忆、few-shot、skills 和工具；
- 验证发送文件、移动端界面与页面稳定访问；
- 重启 MAC 和目标服务后复测；
- 外部开发者不直接修改目标项目。只有 MAC 表现异常时，才可读取必要证据来修复 MAC。

## 完成声明

- 只有 T1–T3：只能说自动代码回归通过。
- 通过 T4：只能说本机真实服务与进程测试通过。
- 通过 T5：才可以说真实飞书私聊 UI 黑盒通过。
- 外部 Provider、完整新项目、旧目录迭代和生成项目分别必须有 T6、T7、T8、T9 证据。
- 任一适用层级失败时，即使其他层级通过，也不能宣称本轮完整完成。
