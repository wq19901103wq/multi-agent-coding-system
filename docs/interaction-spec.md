# MAC 飞书交互规范

状态：实施基线
版本：2026-08-10

本文规定 MAC 在飞书私聊中的用户概念、命令、卡片和状态一致性。文中的“必须”是验收要求，
“应当”是默认产品行为。它描述用户可观察的行为，不规定 Codex 内部工作流。

## 1. 目标和边界

MAC 应当同时提供两种体验：

1. 像 Codex、Claude Code 一样自由输入。用户直接描述新建、修改、调试、解释或补充需求，
   不必先选择任务类型、阶段、角色或 provider。
2. 适合手机操作。系统用卡片完整展示状态和结果；需要用户决定时优先给选择题，命令只作为
   快捷入口。

MAC 不实现 Coordinator、固定研发状态机、关键词意图路由或自定义工具循环。普通消息原样进入
当前项目的持久 Codex Root Thread；Root 自己决定是否直接工作、使用原生子 Agent，或调用外部
coding-agent。

## 2. 用户概念

用户只需要理解 Project；目录、Thread 和 Turn 是其属性，而不是并列的导航对象。

```text
飞书聊天 + 用户
└── 当前 Project（唯一可切换边界）
    ├── 固定工作目录
    └── 当前 Codex Root Thread
        └── 连续 Turn（一条新请求或一次运行中补充）
```

- **目录**：Project 实际读写的工作区。一个 Project 只有一个目录。
- **Project**：长期工作单元，包含固定目录和当前 Root Thread。
- **Thread**：同一 Project 中可连续迭代的 Codex 对话。`/new` 只替换它。
- **Turn**：Thread 内一次执行。Turn 结束表示 Project 回到空闲，不表示 Project 或 Thread 消失。

切换上层对象必须同步刷新其下层状态：切换 Project 后，当前目录和 Thread 必须同时来自新
Project；不得继续显示或使用旧 Project 的目录、Thread、问题或进度。

## 3. 输入规则

### 3.1 自然语言优先

- 除已定义的 slash command 外，任何消息都必须作为自然语言交给当前 Root Thread。
- 系统不得按关键词、错误文案、长度或推测的任务类型选择固定流程。
- 当前没有 Project 时，第一条普通消息必须自动创建一个系统管理的 Project，并执行该消息。
- Owner 不作为普通消息的前置路由。Root 可按需读取当前结果契约；遇到会改变用户可感知结果、授权、
  费用、外部事实或不可逆边界的未决事项时，使用原生 `request_user_input`。问题卡始终先展示，随后
  由隔离 Owner 根据历史权威尝试代答；不能可靠代答时原卡等待用户。技术实现和可撤销试错由 Root 决定。
- 当前 Turn 运行中时，新消息必须使用原生 `turn/steer` 追加到同一 Turn。
- Turn 空闲时，新消息必须在同一 Thread 中开始下一 Turn。

### 3.2 等待用户输入时

- Codex 的 `request_user_input` 必须保持同一 Turn 等待，并始终先投影原问题/审批卡。隔离的
  AI Project Owner 随后判断能否在既有授权内安全代答，不能代答时原卡继续等待用户。
- AI 只能代答依据充分、低风险、可撤销且不改变用户目标的选择。用户偏好、外部事实、凭证、
  新授权、真实费用、发布/外发、删除/覆盖等不可逆事项必须显示问题卡。
- 用户和 AI Project Owner 必须使用同一套“先抢占、再原子提交”的答案协议，先完成者生效，
  后完成者只能看到已处理状态。答案落库后关闭原问题/审批卡，并在最新位置追加用户回执或 Owner
  决策卡。不得先显示成功再写入答案，也不得把后来事实补写回旧卡。
- Codex 原生的命令执行、文件修改和额外权限审批必须使用同一套卡片与 Project Owner 旁路，不能
  因 MAC 使用 `workspace-write` 而静默拒绝 `.git` 等受保护路径，也不能用临时仓库绕过审批。
- 用户点击选项只表示选中；提交后才把答案送回 Codex。
- 问题能穷举时应提供足以覆盖真实取舍的互斥选项，有推荐时排第一；同时必须允许自由输入。
- 普通文字、绝对路径以及未知的 `/...` 内容都可作为问题答案。
- 只有本规范定义的命令可以中止当前待答输入并执行项目控制；不得把 `/Users/...` 等路径误判
  为命令。
- 用户未回答旧问题而输入新的、未引用问题卡的自然语言时，该内容使用原生 `turn/steer` 送入
  同一 Root Turn，但不能据此关闭或回答旧问题。用户消息本身记录补充事实，原问题卡保持原样并
  继续等待。Root 可以处理补充或新话题，原生 `request_user_input` 仍由
  用户在问题卡提交、回复该问题卡，或 Owner 成功代答后解除。
- 回复单个待答问题卡是明确的回答信号；文字作为该题自由文本答案。包含多个待答问题时，必须
  留在原卡逐项选择或填写，MAC 不猜答案对应关系。

消息到达活跃项目时遵循同一组边界，不做关键词判断：

| 到达时状态 | 处理 | 用户可见结果 |
| --- | --- | --- |
| `running` | 原生 `turn/steer` 追加到当前 Turn，同时轮换展示 segment | 原消息出现收到标记；旧进度卡冻结，后续真实活动在最新位置的新进度卡更新 |
| `waiting_user`，未回复问题卡 | steer 到当前 Turn，但不提交答案 | 用户消息记录补充；原问题卡保持待答且不回写 |
| 回复单个待答问题卡 | 提交为该问题答案 | 关闭原问题卡，最新位置追加回执并续接同一 Turn |
| `owner_reviewing` | 新用户消息优先开启或 steer 到 Root 的当前工作 | 旧 Owner 审阅被后续轮次接管，不得晚到覆盖新状态 |
| `idle` 或 native steer 拒绝 | 在同一 Thread 开始下一 Turn | 新建本轮进度卡，消息不丢失、不伪装成旧 Turn 补充 |

### 3.3 消息确认

收到普通消息后，可以给原消息添加轻量确认标记。确认标记只表示“MAC 已收到”，不能替代进度
卡、问题卡、结果卡或错误卡。用户消息本身已经记录到达时间；后续真实执行事件在消息之后的新进度卡更新，
不得为“显示已收到”而跨越时间线修改旧问题或旧进度卡。投影失败不能导致消息再次进入新 Turn。

## 4. 项目命令

命令应短、可记忆，同时保留完整别名。无参数时优先打开卡片；有参数时可以直接完成操作。

| 目的 | 推荐命令 | 兼容命令 | 语义 |
| --- | --- | --- | --- |
| 帮助 | `/help` | `/h` | 展示命令和自然语言用法 |
| 菜单 | `/menu` | `/m` | 展示常用项目操作 |
| 创建 | `/create` | `/c` | 创建系统管理目录中的 Project，并设为当前 |
| 打开 | `/open` | `/o`、`/bind`、`/b` | 打开已有 Git 目录对应的 Project，并设为当前 |
| 项目 | `/proj` | `/ls`、`/projects` | 展示 Project 列表及当前项 |
| 切换 | `/use` | `/s`、`/switch` | 切换当前 Project |
| 当前 | `/info` | `/i`、`/current` | 展示当前 Project、真实目录和运行状态 |
| Coding-Agent | `/agents` | `/agent`、`/a` | 展示实际可用后端、模型和近期运行数据 |
| Project Owner | `/owner` | `/ow` | 查看状态；加 `on` / `off` 可按当前项目启用或关闭 |
| 新对话 | `/new` | `/n`、`/newthread` | 在当前 Project 中开始新 Thread；目录不变 |
| 关闭 | `/close` | `/unbind`、`/u` | 取消当前选择；不删除 Project、目录或 Thread |
| 暂停 | `/pause` | `/p` | 暂停当前 Project |
| 恢复 | `/resume` | `/r` | 恢复当前 Project |
| 停止 | `/stop` | `/x`、`/cancel` | 暂停持续 Goal（如有）并中断当前 Turn；Project 和 Thread 仍保留 |

命令行为必须满足：

- `/open <绝对路径>` 成功后立即把该 Project、目录和 Thread 设为当前；同一用户在同一聊天
  再次打开同一目录时优先恢复原 Project。另一个聊天必须建立独立 Project 和 Thread，不能
  复用对话历史。
- `/use <项目>` 成功后，目录、Thread、进度和待答问题全部切换到所选 Project。
- `/new` 不新建 Project、不改变目录，只清空当前对话绑定；由于 Codex 不持久化空 rollout，新的
  Root Thread 在下一条普通消息到达时创建。命令回执和 `/info` 必须显示“新对话待开始”，且不得
  继续展示旧 Thread 的最近用量。
- `/close` 后普通消息会自动创建新 Project，不允许回退到“最近使用”的旧 Project。
- 未知命令必须显示帮助性错误卡，不静默执行，也不做相似关键词猜测。

## 5. 卡片总则

- 系统主动输出必须进入卡片/outbox；不得混用裸文本作为业务结果。
- 卡片是时间有序的事件记录。只有时间线中最新的活动卡可以原地更新；用户消息、用户提交、菜单
  决定、Owner 决定、问题、审批和后续调整都是新的时间线事件。它们出现后旧卡立即冻结，后续进度
  与终态必须在最新位置新发卡片。Provider 是否继续同一 Turn 不影响展示卡轮换。
- 卡片显示必须来自后台持久状态；刷新、重启或重复事件后，前端不得恢复为旧状态。
- 选项、审批、决定和执行状态属于业务状态，必须前后台一致；原生折叠面板的展开/收起只改变
  当前客户端视图，不改变业务状态，也不要求触发后台回调。
- 卡片用用户能理解的中文说明事实。默认不展示协议字段、Thread ID、子 Agent task path、原始
  工具参数、原始日志或模型私有推理。
- 长内容可以按飞书平台限制拆为多张连续卡片，但不得遗漏内容或让不同轮次互相覆盖。

### 5.1 回复卡片

- 回复卡片是显式上下文选择。MAC 使用卡片持久绑定定位其 Project，不通过用户文字猜测项目；
  回复其他 Project 的卡片时，该 Project 同时成为当前项目。
- 回复运行中进度卡时，消息 steer 到该 Project 的活跃 Turn；回复已完成进度卡或结果卡时，在
  该 Project 当前 Root Thread 开启新 Turn。
- 送入 Root 的内容只包含卡片类型、最多 500 字的用户可见摘要和用户新消息，不重复注入整张
  卡片、工具日志、内部 ID 或旧测试输出。
- 若卡片持久记录仍存在，但所属 Project 已删除或当前用户无权访问，必须明确提示原项目不可用；
  不得把回复静默送入当前 Project。回复普通非 MAC 消息不触发这条项目切换规则。
- 回复单个待答问题的问题卡时，文字作为该问题的自由文本答案并续接原 Turn；一张卡包含多个
  待答问题时不猜对应关系，提示用户在原卡逐项完成。
- 未回复问题卡的普通消息即使在 `waiting_user` 状态到达，也只是同 Turn 补充，不得静默成为
  问题答案；问题卡继续可操作，但不得把这条后来消息回写进旧问题卡。
- `/new` 后回复历史卡不会恢复已废弃的旧 Thread，而是在该 Project 当前 Thread 中携带必要
  摘要继续。
- 回复未绑定到 MAC 卡片的普通消息时，保持当前项目路由，不把任意飞书引用误判为项目切换。
- 失败必须可见；runtime 不得静默切换 provider、伪造恢复步骤或把失败写成成功。

## 6. 卡片类型

### 6.1 项目操作卡

- 菜单、项目列表、创建和打开入口必须清楚区分“新建 Project”“打开已有目录”“切换 Project”
  和“新建对话”。
- 点击按钮后，原卡必须显示已选操作或失效状态，避免用户重复提交。
- 当前项目卡必须至少显示 Project 名称、真实工作目录和当前运行状态。
- 当前项目卡只展示 Provider 真正报告的费用；没有可核验费用时明确显示费用未知，不得把
  未知值显示为 `$0`。有原生 token 数据时展示最近一轮真实用量。

### 6.2 问题卡

- 初始状态显示问题、必要上下文、实际选项（若适用）和自由输入入口。
- 标题只描述用户动作（例如“需要你确认 1 个问题”）；项目和执行者作为底部次要信息，
  不得把 `conversation`、`root_agent`、Turn 等内部协议词放进标题或回执。
- 点击选项后原卡可暂时显示“已选：…”；后台尚未提交时仍显示等待状态。
- 提交后关闭原问题卡，在用户消息之后追加“已提交：…”回执；后台答案与最新回执必须一致。
- 重复点击或重复回调必须幂等，不得让同一 Turn 收到两次答案。

### 6.3 Owner 决定与建议

- AI Project Owner 响应 Root 已经发出的原生 `request_user_input`，并在每个成功、失败或中断的
  用户可见终态展示后审阅一次。它是用户级代理，不是 Coordinator，不创建研发阶段，也不替 Root
  处理普通技术细节。
- 原问题/审批卡必须先成功发送。AI 可代答时，原交互关闭，Owner 决定、折叠依据和“调整决定”
  作为较晚发生的决策卡追加在最新位置；不得跨过用户消息修改旧卡。
- 汇报卡必须先完整展示；长汇报拆成多张卡时只在最后一张成功展示后审阅一次。若存在真实、尚未
  解决且可安全代做的 Owner 决策，决定追加在同一结果卡；若缺少用户偏好或存在需要用户确认的
  真实取舍，先结束结果卡，再在时间线最新位置新发可操作建议/选择卡。没有决定或有用建议时不生成卡片。
- 每次汇报审阅都必须保存结构化审阅记录，包括 `decide`、`require_user` 和 `advise`。汇报最后一张卡
  先原地显示“Project Owner · 审阅中”，结束后更新为至少一条具体意见与耗时；无需继续执行的意见
  直接留在原汇报卡，并保持 `continue_execution=false`。
- 完整汇报送达后必须先落一条待审阅记录，再异步调用 Owner；审阅不得占用项目执行锁或延迟用户
  下一条消息。服务重启后恢复待审阅/审阅中的记录，同一个 Root 结果不得重复审阅或重复发卡。
- Owner 审阅期间若用户或 Root 已产生更新的执行轮次，旧审阅只能标记为“后续消息已接管”，不得
  更新 Owner 审阅状态、追加决定或启动新的 Root Turn。
- 同一 Root Turn 中已经展示并生效的问题/审批决定必须随最终汇报提供给隔离 Owner。已经解决的
  事项不得再次生成决定卡；汇报后的 `decide` 可以是继续执行，也可以是接受结果、结束当前事项、
  保持等待或拒绝某条路线。只有 `continue_execution=true` 才启动下一轮 Root 执行。
- 没有待决策事项、但存在具体、当前有用且不重复汇报内容的建议时，可以在汇报后追加精简的
  “AI 建议”卡。空泛的“继续优化”“保持关注”不得生成建议卡，建议也不得自动启动执行。
- 每条建议都必须至少提供一项可操作建议；存在真实取舍时提供实际互斥选项，有推荐时排第一，不为凑数编造方案，需要时可提供
  替代方案。每个选项显式声明是需要 Root 执行，还是只记录选择并保持现状；用户点击后原卡显示
  已选结果，只有执行型选项才启动新的 Root 轮次。
- 已选定、已授权且未完成的工作继续推进，不为普通执行步骤反复提问；尚未选定的下一步方向给出推荐与真实备选，用户选择前不执行。
- 每次真人提交选择，项目事件日志保存当时的公开上下文、问题、实际可见选项、最终选择、选择人和来源；Owner 建议同时保存关联的真人上下文和已送达汇报。
  后续 Owner 按当前问题检索这些案例，结合当时的取舍学习。普通选项选择不是对推荐的纠正；只有明确调整才作为纠正反例。一次性选择不自动升级为长期原则或新的授权，其他项目的对话和汇报不随案例共享。
- 汇报决定需要执行 Agent 继续工作时，只有决定所在结果卡或选择卡成功展示后才把决定送回同一 Root Thread；
  不需要继续执行的判断归入审阅结论或建议，不生成重复决定卡，也不制造额外 Turn。
- Project Owner 与刚刚执行任务的 Root、子 Agent 和外部 coding-agent 使用独立临时 Thread、
  独立 cwd 和独立最小上下文，不共享执行 Agent 的隐藏对话、prompt、reasoning 或工具输出。
- Owner 的用户身份由 `open_id` 关联：跨项目只读取有用户原话证据的生效策略；一次性选择保留在对应项目的
  决定账本。Owner 不另建目标状态或自动唤醒链。
- `ProjectPolicy` 只保存用户明确长期表达，或至少两处独立真人来源支持的原则，必须保留逐字证据和来源；
  单次选择保留为带上下文的选择案例，不自动变成长期原则。执行汇报、Owner 判断与技术建议不能写入或覆盖，用户纠正时只允许精确替代旧规则。
- 每轮 Owner 默认先获得当前真人指令、ProjectPolicy、全部生效用户策略和未完成承诺，
  再获得当前执行汇报、最近决定和最近 5 轮管理历史；更早完整历史与纯真人指令历史分别通过只读
  管理工具分页读取。Owner 不读取项目源码，技术审查和验收由 Root 动态委派专业 Agent。
  当前 Root 汇报只是待审查声明；与人类规则、未完成决定或证据冲突时必须显示纠正或建议，每轮都不得静默结束。
- 汇报卡的 Owner 页脚展示当前结论和执行状态。Owner 的依据、来源、记忆/规则变化放在可展开的
  “Owner 审阅详情”；模型和 Token 放在独立的次要折叠区。
  用户可用 `/owner`（`/ow`）查看当前项目的 Owner 状态、用户明确的 ProjectPolicy、
  未完成承诺、最近项目记录和跨项目偏好。最近项目记录按“用户原文、所回应的
  可见卡片/决定、当轮结果”保留上下文；任何带回应对象的用户指令都必须结合该对象理解。
  `/owner off` 仅关闭当前项目
  后续的汇报审阅、问题代答和审批代答，原问题仍直接交给用户，`/owner on` 恢复。
- 每份 Root 汇报必须携带 `request_origin`。只有 `human` 来源的用户原话可作为新增授权和偏好证据；
  `project_owner` 或 `system_recovery` 生成的文字不是用户授权。Owner 推动的执行必须关联原
  `parent_decision_id`，后续只更新同一决定的完成、继续、阻塞或调整状态，不得递归自我授权。
- `system_recovery` 只表示恢复传输，不得覆盖原始历史轮次的授权来源。恢复同一轮后生成的汇报审阅
  必须继承该轮持久记录中的 `request_origin` 和 `parent_decision_id`。
- 用户在本轮请求中明确表达的长期偏好可进入用户级显式偏好表，但必须同时保存可在用户原话中逐字
  找到的 evidence、时间、来源 Project 和公开结果引用。项目一次性需求、执行汇报和 Agent 推断
  不能成为跨项目偏好；冲突时由 Owner 按较新明确证据判断，不得静默覆盖旧证据。
- 决策上下文只能包含：当前用户可读问题或汇报、同项目每轮用户指令/当轮目标/已送达汇报、ProjectPolicy、
  历史决策卡、同一用户跨项目明确提交过的选择与决策调整，以及白名单只读管理工具。跨项目记录
  必须带项目和时间，只作为偏好证据；不得注入隐藏对话、reasoning、测试日志、其他 Project 内容、
  卡片回调 payload 或凭证。
- 例行汇报审阅不得注入整段 Root 对话：默认提供当前轮、最近 5 轮和全部生效用户偏好；确实需要
  更早依据时再调用 `read_project_history` 或其他白名单只读工具。不得读取执行 Agent 的 prompt、
  reasoning、原始工具输出、完整对话或其他目录。
- AI 没有足够把握时不得代答。原问题/审批卡继续可操作；Owner 只是把已有问题交还用户时不生成
  重复评估卡。只有形成了新的、有用的建议或需要解释的边界判断时，才在后方追加独立评估卡。
- 原问题卡展示后，用户和 Owner 都可以成为第一响应者。后台必须原子认领同一 interaction：用户
  已提交时丢弃迟到的 Owner 结果；Owner 已认领时阻止重复用户提交；Owner 在答案原子提交前应用
  失败时恢复 `pending`，继续让用户处理。答案已经提交后，原问题卡或决策卡发送失败只由 outbox
  重试，不能回滚已返回同一 Codex turn 的答案。
- 决策卡与进度卡必须使用同一视觉层级：上方显示主要内容；事项、依据、影响和是否可调整收进
  位于原内容位置的“···”原生折叠面板；其下以次要小字显示执行者和耗时；最下方使用默认折叠的
  “Agent 与用量详情”展示实际 Agent、模型和分项 Token。模型或 Token 无法取得时明确显示
  “后端未报告”，不得编造。绿色表示已应用，橙色表示等待用户调整，蓝色表示调整已送入执行，
  红色表示未能应用。
- 可撤销决定提供“调整决定”按钮；用户也可直接回复该卡。点击后在最新位置追加输入提示；用户
  提交后再追加调整记录并定位到该决定所属 Project，后台同步更新，再 steer 活跃 Turn 或在同一
  Root Thread 开始下一 Turn。旧决定卡不得补写用户后来提交的原文。
- 决策卡成功送达但答案未能持久化时，必须把同一张卡改成红色“未应用”，并显示问题卡询问
  用户；不得保留假成功。

### 6.4 进度卡

每个连续执行片段只有一张主进度卡，并持续原地更新。出现问题卡或审批卡时，必须先冻结当时的
进度卡，再按真实时间追加问题/审批卡；交互解决后关闭旧卡，并在最新位置追加选择回执或 Owner
决策卡，然后在它们
下方新建后续进度卡。不得跨过更新的卡片继续修改上方旧进度卡，否则“最新发生的事”会回到历史
位置。一次没有阻塞交互的 Turn 仍然只有一张主进度卡。

运行中接受补充消息后，不新增“已收到”卡；用户消息本身已经是时间线事件。后续真实执行活动可在
当前进度卡中反映，但若进度卡已因问题/审批被冻结，则不得更新问题前的任何历史卡。

已处理的原生审批卡只保留选择结果和准确终态，命令、目录、原因收进原位置的“···”折叠面板，
不再显示失效按钮；`cancel` 必须显示本轮已停止，不能写成仍在继续处理。它必须展示：

- 每轮以用户本轮可见请求作为第一个大步骤，保证 Codex 直接回答且没有 commentary 或工具事件时，
  卡片仍有真实步骤；后续公开进展可以继续细化步骤历史。

- 卡片颜色直接表达整轮状态：蓝色为运行中、绿色为完成、红色为失败；不得再用“本轮正在做”
  “本轮处理完成”等正文重复颜色已经表达的状态；
- “执行步骤”位于卡片上方并默认展开，按时间顺序同时显示已完成的大步骤、当前大步骤及当前
  步骤内可观察的工具、文件、验证、原生 Child Agent 和外部 provider 活动；
- 步骤下方以次要小字显示当前执行主体、已等待时间和最近活动时间；
- “Agent 与用量详情”紧随执行元数据并默认折叠。用户展开后可以查看本轮真实执行链、Agent
  数量与状态、Root、原生 Child Agent、外部 provider、模型、选择原因、最近活动和分项
  Token。未实际调用的 Agent 不出现；
- 并行调用必须在步骤和 Agent 详情中显示为并行分支，不能用串行箭头误导用户；不再设置独立
  的“执行链路”区域，避免同一事实重复出现。

分项 Token 中，Codex Root、原生 Child Agent 和外部 provider 不得混成一个无法核验的数字；
缓存命中按后端原始口径区分“输入中缓存”或独立“缓存读取”。后端未报告模型或 usage 时明确
显示“后端未报告”，可核验合计必须注明未包含的执行项。

视觉层级参考 cc-connect 的飞书 rich card：颜色先表达状态，默认展开的“执行步骤”表达任务
内容，再到下方可展开的“Agent/模型/用量”。手机首屏必须能判断是否仍在运行、正在做什么和
执行到了哪里；低频元数据放入折叠面板，需要时再展开，不与任务内容争夺注意力。

执行步骤卡、AI 决策卡及后续所有执行相关卡片必须复用这一层级和同一套折叠组件，不得分别使用
“查看详情”“查看依据”等不同按钮重新发明展示交互。`···` 表示在当前时间/内容位置被折叠的
正文，Agent/模型/耗时/Token 始终位于卡片下方的统一元数据区域。

步骤只能由真实事件产生：

- Root 的公开 commentary 可以开启或更新一个大步骤；
- 不得把用户输入原样复述成“处理你的请求：……”大步骤；大步骤标题只概括实际工作，手机视图
  最多保留 100 字；
- 一次明确的外部 provider 调用构成一个大步骤；该 provider 内的说明、工具和结果是其小步骤；
- 后续事件可以结束当前大步骤，但不能删除先前 provider 历史；
- 没有事件依据时不得显示百分比、阶段结论或“已通过”；
- 私有 reasoning 的 started/completed 等协议生命周期不是用户步骤，不进入历史；
- 不展示 chain-of-thought、敏感工具参数和大段原始输出；允许展示经过脱敏和截断的命令、文件、
  工具名称与结果摘要，使每条活动都能回答“刚刚具体做了什么”。

运行中视图保留最近 8 个大步骤，并且只为当前仍在运行的大步骤展示最近 7 个小步骤。更多历史
不得丢弃或显示成解释性废话，而是收进标题为“···”的折叠区域，用户点击即可展开。大步骤结束
后不再显示它的小步骤；Turn 结束后只保留大步骤，完整结果和验证细节由结果卡汇报。

### 6.5 结果卡

结果卡必须完整说明：

- 做成了什么，或为什么没有做成；
- 用户可观察的改动和关键文件/入口；
- 实际执行的验证层级及结果；
- 可以直接访问的地址、文件或下一步；
- 真实阻塞、未验证项和失败 provider。

运行结束只把 Project 设为空闲。结果卡不得暗示 Project 已关闭或对话已丢失。

## 7. Coding-agent 与模型展示

- 默认执行者是当前 Project 的 Codex Root；Root 从首轮起拥有完整 coding tools、skills 和原生
  multi-agent 能力。
- Root 可以按任务需要调用 Claude Code、Kimi Code、Pi 或外部 Codex CLI；MAC 不按关键词或
  固定角色自动路由，也不自动 fallback。
- 所有已启用 provider 及其能力说明必须作为动态工具提供给 Root，选择权在 Root。
- `/agents` 必须区分“可用”“配置但未启用”和“配置启用但当前不可用”，并展示近期进程完成
  数据；不得把 Zcode 等未启用后端宣传成已经支持。
- 卡片展示实际发生的执行者和模型，不展示“理论可用”但本轮未调用的 provider。
- provider 选择、成功、失败和切回 Root 都必须保留在进度历史中。
- 不同 provider 或模型不能共享模型侧 Prompt/KV Cache。简单任务不应为了展示多后端而委派；
  原生 Child Agent 的连续工作优先续接同一 thread，同一外部调用只传完成任务所需的最小上下文。
  MAC 不复制完整 Root 历史来伪造跨 provider 缓存。

## 8. 隔离与恢复

- 当前 Project 的选择以“飞书聊天 + 用户”为边界；不同聊天不得共享当前 Project。
- 即使是同一用户和同一目录，不同聊天也不得自动复用 Project 或 Root Thread；只有同一聊天
  内重新打开目录才能自动续接。
- 不同 Project 的 Thread、Turn、问题、进度和对话历史必须隔离。
- 同一 Project 可以读取其工作目录；读取其他目录属于 coding-agent 的正常文件权限，但其他
  Project 的聊天内容不得因此注入当前上下文。
- 服务重启后必须恢复 Project 与 Root Thread identity、卡片投影和空闲/运行状态；旧 active turn
  和待答请求先如实中断。存在原用户请求时，在同一 Root Thread 自动发起安全续接轮，先检查已
  完成状态再继续；已经完成、仅后处理被中断的 turn 不得重复执行。不得靠“最近项目”猜测当前选择。

## 9. 响应与停滞

- 收到消息后应尽快出现确认或进度卡，不能在模型完成前保持无反馈。
- 每个 Turn 必须记录调度、运行开始、Thread 就绪、`turn/started`、首个 item、首个工具、
  首张进度卡、`turn/completed`、结果卡的相对耗时；优化必须依据这些真实边界。
- 有真实事件时立即更新进度；长时间无新事件时仍应更新已等待时间和最后活动时间。
- 停滞提示只能陈述可观察事实，不猜测模型在“深入思考”或虚构当前工作。
- 用户可随时 `/stop`；持续 Goal 必须先暂停，当前 Turn 使用原生事件报告的实时 ID 中断；结果必须显示在卡片上，且后续可以继续同一 Project。

## 10. 验收矩阵

实现至少覆盖以下可观察场景：

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| UX-01 | 无 Project 直接输入需求 | 自动创建 Project，出现进度卡并执行 |
| UX-02 | `/open` 已有目录 | 当前 Project、目录和 Thread 同时切换 |
| UX-03 | `/new` | Project/目录不变，Thread 更新 |
| UX-04 | `/close` 后输入 | 不恢复旧 Project，自动创建新 Project |
| UX-05 | 运行中补充 | 进入同一 Turn，不新建并行执行；旧进度卡冻结，消息之后的新进度卡显示已收到的补充摘要 |
| UX-06 | 选择题 | 已选、已提交、后台答案三者一致，重复提交幂等 |
| UX-07 | 待答时发送绝对路径 | 路径作为答案，不报未知命令 |
| UX-08 | 多 Project 切换 | 目录、Thread、问题和进度不串线 |
| UX-09 | Root 工具与 commentary | 同一进度卡显示大步骤及小步骤历史 |
| UX-10 | 外部 provider | 卡片显示真实 provider、模型、原因、活动和结果 |
| UX-11 | provider 失败 | 原样可见，无静默 fallback、无假成功 |
| UX-12 | 长时间无事件 | 显示已等待和最后活动，不显示假进度 |
| UX-13 | 服务重启 | 当前 Project/Thread 和卡片状态可恢复；未完成请求自动安全续接，已完成 turn 不重跑 |
| UX-14 | 完成结果 | 结果、验证、入口和未完成项信息完整 |
| UX-15 | 飞书真实界面 | 输入、点击、旧交互关闭、最新回执和后台状态在 T5 中一致 |
| UX-16 | Provider 目录 | `/agents` 与实际配置、可执行后端和近期样本一致 |
| UX-17 | 费用与 Token | 按 Root、Child Agent、外部 provider 分项显示真实用量和缓存口径；未知项不计入可核验合计，未知费用不显示为 `$0` |
| UX-18 | AI 可代答决定 | 原问题/审批卡先出现；Owner 代答后关闭旧交互并在最新位置追加决定，再在同一原生 request 中继续 |
| UX-19 | AI 不可代答决定 | 偏好、授权、外部事实、凭证、费用或不可逆操作仍显示问题卡 |
| UX-20 | 调整 AI 决定 | 按钮或直接回复在最新位置追加调整记录，并路由到原 Project 的当前 Root Thread |
| UX-21 | 汇报后 Owner 判断 | 完整汇报先展示；有把握的决定追加在结果卡，需要用户确认的建议在最新位置新发选择卡 |
| UX-22 | Codex 原生审批 | 命令、文件、权限审批可由 AI 高把握代决或由用户在原卡提交，并把原生响应送回同一 Turn |
| UX-23 | 跨项目偏好 | 只共享同一用户明确选择的带时间证据，不共享其他项目对话；存在有意义但低把握的方向判断时显示具体建议，有真实取舍时显示实际互斥选项 |
| UX-24 | 待答时发送新话题 | 新消息 steer 到同一 Turn；原问题不被误答且旧问题卡不被回写，后续可见进度只能出现在新卡 |
| UX-25 | Turn 边界竞争 | native steer 拒绝时消息只进入下一 Turn 一次，旧进度卡不显示虚假接收 |
| UX-26 | 运行中追加消息 | native steer 可保持同一 Turn，但旧进度卡冻结；“已收到补充”、后续活动和终态只出现在消息之后的新卡 |

自动测试负责 UX-01 至 UX-14 的快速回归；涉及卡片交互的改动必须再做真实飞书 T5。T5 的
定义和证据要求以 `docs/testing-taxonomy.md` 为准。
