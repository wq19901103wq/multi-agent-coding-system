# MAC 飞书交互规范

状态：实施基线
版本：2026-08-05

本文规定 MAC 在飞书私聊中的用户概念、命令、卡片和状态一致性。文中的“必须”是验收要求，
“应当”是默认产品行为。它描述用户可观察的行为，不规定 Codex 内部工作流。

## 1. 目标和边界

MAC 应当同时提供两种体验：

1. 像 Codex、Claude Code 一样自由输入。用户直接描述新建、修改、调试、解释或补充需求，
   不必先选择任务类型、阶段、角色或 provider。
2. 适合手机操作。系统用卡片完整展示状态和结果；需要用户决定时优先给选择题，命令只作为
   快捷入口。

MAC 不实现 Coordinator、固定研发状态机、关键词意图路由或自定义工具循环。普通消息原样进入
当前项目的持久 Codex Root Thread；Root 自己决定是否直接工作、使用原生子 Agent，或调用外部
coding-agent。

## 2. 用户概念

用户只需要理解 Project；目录、Thread 和 Turn 是其属性，而不是并列的导航对象。

```text
飞书聊天 + 用户
└── 当前 Project（唯一可切换边界）
    ├── 固定工作目录
    └── 当前 Codex Root Thread
        └── 连续 Turn（一条新请求或一次运行中补充）
```

- **目录**：Project 实际读写的工作区。一个 Project 只有一个目录。
- **Project**：长期工作单元，包含固定目录和当前 Root Thread。
- **Thread**：同一 Project 中可连续迭代的 Codex 对话。`/new` 只替换它。
- **Turn**：Thread 内一次执行。Turn 结束表示 Project 回到空闲，不表示 Project 或 Thread 消失。

切换上层对象必须同步刷新其下层状态：切换 Project 后，当前目录和 Thread 必须同时来自新
Project；不得继续显示或使用旧 Project 的目录、Thread、问题或进度。

## 3. 输入规则

### 3.1 自然语言优先

- 除已定义的 slash command 外，任何消息都必须作为自然语言交给当前 Root Thread。
- 系统不得按关键词、错误文案、长度或推测的任务类型选择固定流程。
- 当前没有 Project 时，第一条普通消息必须自动创建一个系统管理的 Project，并执行该消息。
- 当前 Turn 运行中时，新消息必须使用原生 `turn/steer` 追加到同一 Turn。
- Turn 空闲时，新消息必须在同一 Thread 中开始下一 Turn。

### 3.2 等待用户输入时

- Codex 的 `request_user_input` 必须投影为问题卡，并在后台保持同一 Turn 等待。
- 用户点击选项只表示选中；提交后才把答案送回 Codex。
- 问题能穷举时应提供 2–3 个互斥选项，推荐项排第一；同时必须允许自由输入。
- 普通文字、绝对路径以及未知的 `/...` 内容都可作为问题答案。
- 只有本规范定义的命令可以中止当前待答输入并执行项目控制；不得把 `/Users/...` 等路径误判
  为命令。
- 用户未回答旧问题而输入新的自然语言时，该内容仍送回等待中的 Root，由 Root 判断它是在
  回答、补充还是切换话题；MAC 不自行分类。

### 3.3 消息确认

收到普通消息后，可以给原消息添加轻量确认标记。确认标记只表示“MAC 已收到”，不能替代进度
卡、问题卡、结果卡或错误卡。

## 4. 项目命令

命令应短、可记忆，同时保留完整别名。无参数时优先打开卡片；有参数时可以直接完成操作。

| 目的 | 推荐命令 | 兼容命令 | 语义 |
| --- | --- | --- | --- |
| 帮助 | `/help` | `/h` | 展示命令和自然语言用法 |
| 菜单 | `/menu` | `/m` | 展示常用项目操作 |
| 创建 | `/create` | `/c` | 创建系统管理目录中的 Project，并设为当前 |
| 打开 | `/open` | `/o`、`/bind`、`/b` | 打开已有 Git 目录对应的 Project，并设为当前 |
| 项目 | `/proj` | `/ls`、`/projects` | 展示 Project 列表及当前项 |
| 切换 | `/use` | `/s`、`/switch` | 切换当前 Project |
| 当前 | `/info` | `/i`、`/current` | 展示当前 Project、真实目录和运行状态 |
| 新对话 | `/new` | `/n`、`/newthread` | 在当前 Project 中开始新 Thread；目录不变 |
| 关闭 | `/close` | `/unbind`、`/u` | 取消当前选择；不删除 Project、目录或 Thread |
| 暂停 | `/pause` | `/p` | 暂停当前 Project |
| 恢复 | `/resume` | `/r` | 恢复当前 Project |
| 停止 | `/stop` | `/x`、`/cancel` | 中断当前 Turn；Project 和 Thread 仍保留 |

命令行为必须满足：

- `/open <绝对路径>` 成功后立即把该 Project、目录和 Thread 设为当前；同一用户再次打开同一
  目录时优先恢复原 Project，而不是重复创建。
- `/use <项目>` 成功后，目录、Thread、进度和待答问题全部切换到所选 Project。
- `/new` 不新建 Project、不改变目录，只创建新的 Root Thread。
- `/close` 后普通消息会自动创建新 Project，不允许回退到“最近使用”的旧 Project。
- 未知命令必须显示帮助性错误卡，不静默执行，也不做相似关键词猜测。

## 5. 卡片总则

- 系统主动输出必须进入卡片/outbox；不得混用裸文本作为业务结果。
- 同一个交互对象必须原地更新：菜单选择、问题选择、问题提交和进度变化不能靠新增重复卡片
  表示。
- 卡片显示必须来自后台持久状态；刷新、重启或重复事件后，前端不得恢复为旧状态。
- 卡片用用户能理解的中文说明事实。默认不展示协议字段、Thread ID、子 Agent task path、原始
  工具参数、原始日志或模型私有推理。
- 长内容可以按飞书平台限制拆为多张连续卡片，但不得遗漏内容或让不同轮次互相覆盖。
- 失败必须可见；runtime 不得静默切换 provider、伪造恢复步骤或把失败写成成功。

## 6. 卡片类型

### 6.1 项目操作卡

- 菜单、项目列表、创建和打开入口必须清楚区分“新建 Project”“打开已有目录”“切换 Project”
  和“新建对话”。
- 点击按钮后，原卡必须显示已选操作或失效状态，避免用户重复提交。
- 当前项目卡必须至少显示 Project 名称、真实工作目录和当前运行状态。

### 6.2 问题卡

- 初始状态显示问题、必要上下文、2–3 个选项（若适用）和自由输入入口。
- 点击选项后原卡显示“已选：…”；后台尚未提交时仍显示等待状态。
- 提交后原卡显示“已提交：…”，所有提交按钮失效，后台答案与卡片文字必须一致。
- 重复点击或重复回调必须幂等，不得让同一 Turn 收到两次答案。

### 6.3 进度卡

每个 Turn 只能有一张主进度卡，并持续原地更新。它必须展示：

- 当前真实状态和已等待时间；
- 最近一次真实活动及距今时间；
- 当前执行主体和实际模型；后端没有报告模型时显示“后端未报告”；
- 使用外部 provider 时显示 provider 与选择原因；
- 已完成的大步骤历史；
- 当前大步骤及其最近的小步骤历史；
- 可观察的工具、文件、验证、原生 Child Agent 和外部 provider 活动。

步骤只能由真实事件产生：

- Root 的公开 commentary 可以开启或更新一个大步骤；
- 一次明确的外部 provider 调用构成一个大步骤；该 provider 内的说明、工具和结果是其小步骤；
- 后续事件可以结束当前大步骤，但不能删除先前 provider 历史；
- 没有事件依据时不得显示百分比、阶段结论或“已通过”；
- 不展示 chain-of-thought、私有 reasoning、工具原始参数和大段原始输出。

历史可以为手机屏幕限长，但必须保留最近的完整上下文：已完成大步骤最多 8 条，当前大步骤的
最近小步骤最多 7 条；被截断时应明确使用“更早步骤已收起”等提示，而不是悄悄丢失。

### 6.4 结果卡

结果卡必须完整说明：

- 做成了什么，或为什么没有做成；
- 用户可观察的改动和关键文件/入口；
- 实际执行的验证层级及结果；
- 可以直接访问的地址、文件或下一步；
- 真实阻塞、未验证项和失败 provider。

运行结束只把 Project 设为空闲。结果卡不得暗示 Project 已关闭或对话已丢失。

## 7. Coding-agent 与模型展示

- 默认执行者是当前 Project 的 Codex Root；Root 从首轮起拥有完整 coding tools、skills 和原生
  multi-agent 能力。
- Root 可以按任务需要调用 Claude Code、Kimi Code、Pi 或外部 Codex CLI；MAC 不按关键词或
  固定角色自动路由，也不自动 fallback。
- 所有已启用 provider 及其能力说明必须作为动态工具提供给 Root，选择权在 Root。
- 卡片展示实际发生的执行者和模型，不展示“理论可用”但本轮未调用的 provider。
- provider 选择、成功、失败和切回 Root 都必须保留在进度历史中。

## 8. 隔离与恢复

- 当前 Project 的选择以“飞书聊天 + 用户”为边界；不同聊天不得共享当前 Project。
- 不同 Project 的 Thread、Turn、问题、进度和对话历史必须隔离。
- 同一 Project 可以读取其工作目录；读取其他目录属于 coding-agent 的正常文件权限，但其他
  Project 的聊天内容不得因此注入当前上下文。
- 服务重启后必须恢复 Project 与 Root Thread identity、待答问题、卡片投影和空闲/运行状态；
  不得靠“最近项目”猜测当前选择。

## 9. 响应与停滞

- 收到消息后应尽快出现确认或进度卡，不能在模型完成前保持无反馈。
- 有真实事件时立即更新进度；长时间无新事件时仍应更新已等待时间和最后活动时间。
- 停滞提示只能陈述可观察事实，不猜测模型在“深入思考”或虚构当前工作。
- 用户可随时 `/stop`；中断结果必须显示在原进度/结果卡上，且后续可以继续同一 Project。

## 10. 验收矩阵

实现至少覆盖以下可观察场景：

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| UX-01 | 无 Project 直接输入需求 | 自动创建 Project，出现进度卡并执行 |
| UX-02 | `/open` 已有目录 | 当前 Project、目录和 Thread 同时切换 |
| UX-03 | `/new` | Project/目录不变，Thread 更新 |
| UX-04 | `/close` 后输入 | 不恢复旧 Project，自动创建新 Project |
| UX-05 | 运行中补充 | 进入同一 Turn，不新建并行执行 |
| UX-06 | 选择题 | 已选、已提交、后台答案三者一致，重复提交幂等 |
| UX-07 | 待答时发送绝对路径 | 路径作为答案，不报未知命令 |
| UX-08 | 多 Project 切换 | 目录、Thread、问题和进度不串线 |
| UX-09 | Root 工具与 commentary | 同一进度卡显示大步骤及小步骤历史 |
| UX-10 | 外部 provider | 卡片显示真实 provider、模型、原因、活动和结果 |
| UX-11 | provider 失败 | 原样可见，无静默 fallback、无假成功 |
| UX-12 | 长时间无事件 | 显示已等待和最后活动，不显示假进度 |
| UX-13 | 服务重启 | 当前 Project/Thread 和卡片状态可恢复 |
| UX-14 | 完成结果 | 结果、验证、入口和未完成项信息完整 |
| UX-15 | 飞书真实界面 | 输入、点击、原卡更新和后台状态在 T5 中一致 |

自动测试负责 UX-01 至 UX-14 的快速回归；涉及卡片交互的改动必须再做真实飞书 T5。T5 的
定义和证据要求以 `docs/testing-taxonomy.md` 为准。
