# MAC 开发与黑盒验证章程

## 对象边界

1. **MAC 系统**：本仓库的 Root runtime、飞书适配、项目管理、外部 Agent 后端、卡片、
   持久化、计费和测试。开发者可以检查并修改。
2. **参考项目**：用户授权 Root Agent 读取的能力来源。是否复制代码、数据、Prompt、skills、
   few-shot 和工具，由用户目标及源项目事实决定。
3. **生成项目**：MAC 的交付对象。开发者不能直接替它实现或修复，只能通过 MAC 对话驱动。

## MAC 开发模式

允许检查 MAC 源码、数据库、日志、app-server 事件和飞书投影。修复必须位于 MAC 层，且：

- 对准通用根因；
- 不增加关键词和单 case 分支；
- 不重新实现 Codex 已有能力；
- 增加相应协议或入口回归测试；
- 修改后重启真实服务验证。

当仅凭 MAC 日志无法解释生成项目异常时，可以最小范围只读检查生成项目；不得直接修改。

## 黑盒模式

黑盒操作者只使用真实产品入口：飞书私聊、项目网站、CLI 或 App。不能用源码、数据库、
内部日志和测试注入端点证明黑盒通过。

每次报告必须说明：

- 使用的入口；
- 操作者是真人还是自动化；
- 原始输入；
- 可见输出和等待时间；
- 是否经过真实飞书传输；
- 尚未证明的内容。

详细术语以 [testing-taxonomy.md](testing-taxonomy.md) 为准。

## 个人 Agent 项目专项

最终必须通过 MAC 自己完成个人 Agent 项目的修改，外部开发者不能直接改目标项目。黑盒至少
覆盖：

- 身份与个人说话风格；
- 已授权人物记忆及跨轮连续性；
- mac-rpa 的 few-shot、skills、知识和工具能力；
- 文件发送；
- 页面视觉与移动端体验；
- 服务重启后仍可访问；
- 已有项目上的继续修改与 debug。

发现问题后，把用户可见证据作为下一条消息交给同一个 Root Thread；Root Agent 自行定位、
修改和验证。MAC 本身不符合预期时，暂停项目黑盒，修 MAC 后从真实入口重测。

## 完成条件

不得只凭 pytest 或脚本状态宣称完成。执行内核修改至少需要：

1. T1/T2 自动测试通过；
2. 真实 Codex app-server 回合通过；
3. T5 真实飞书私聊 UI 完成新建、修改、debug 和问题卡交互；
4. T7 个人 Agent 真实页面黑盒通过；
5. 日志没有未解释的 Root turn、卡片或 app-server 协议错误。
