# MAC 开发与黑盒验收工作章程

> 状态：生效  
> 日期：2026-07-26  
> 适用范围：`multi-agent-coding-system` 的后续优化，以及由 MAC 生成项目的真实端到端验收

测试层级、真实飞书群与真实私聊的区别、黑盒证据边界以及完成声明，统一遵循 [`testing-taxonomy.md`](testing-taxonomy.md)。本章程中的“真实入口”不自动等于真实私聊；必须在报告中明确 T1-T9 分类。

## 1. 目的

本工作的目标不是由外部开发者直接完成某个生成项目，而是持续验证和改进 MAC，使 MAC 能够通过真实用户对话独立完成以下闭环：

1. 理解用户需求和参考项目；
2. 形成完整、无隐含冲突的交付合同；
3. 将必要事实分别提供给 Planner、Coder、Tester 和 Reviewer；
4. 在信息不足、环境阻塞或质量失败时正确协调；
5. 完成编码、测试、评审、返工和用户验收；
6. 最终交付一个从真实用户入口可验证的项目。

生成项目是用于检验 MAC 能力的测试对象。外部开发者不得绕过 MAC 直接帮助生成项目通过验收。

## 2. 三个对象必须分开

### 2.1 MAC 系统

MAC 是被开发和调试的系统，包括：

- Coordinator 与 Orchestrator；
- Planner、Coder、Tester、Reviewer 等 Agent；
- Prompt、Schema、few-shot 和 Agent 合同；
- 状态机、事实、反馈、审批和澄清机制；
- Runtime、worktree、任务重试和恢复；
- 飞书消息、卡片、通知和管理接口；
- MAC 自身的数据库、日志和自动化测试。

外部开发者有权查看和修改这些内容。

### 2.2 参考项目

参考项目是 MAC 理解目标能力的证据来源，不等于目标项目的实现模板。

MAC 内部 Agent 可以在授权范围内读取参考项目，盘点身份、人设、记忆、行为、工具、约束和运行方式。外部验收者在黑盒测试期间不得替 MAC 阅读参考代码、总结实现或把具体实现方案直接告诉 Coder。

“完整参考”表示完整盘点参考项目表现出的产品能力，不表示无条件复制参考项目的全部技术栈和外部依赖。

必须区分：

- **产品能力**：用户能够感知或明确要求的行为；
- **目标合同**：本次目标项目确定需要实现和验收的能力；
- **承载方式**：参考项目用于实现能力的技术手段和外部集成。

承载方式只有在目标合同明确需要时才进入实现范围。例如，参考项目使用 WeFlow 连接微信，不代表一个个人网站默认必须依赖 WeFlow 或要求用户登录微信。

### 2.3 生成项目

生成项目是 MAC 的交付结果和黑盒验收对象。

在外部黑盒验收模式下，外部开发者默认不得：

- 查看或修改生成项目业务源码；
- 查看生成项目 `.mac/` 产物；
- 查看生成项目 diff、内部日志、数据库、SSE 原文或工具参数；
- 绕过 MAC 运行代码级诊断后把修改位置告诉 Coder；
- 手工复制参考项目能力到生成项目。

生成项目的源码定位、实现、白盒测试和修复原则上由 MAC 内部 Agent 完成。只有为诊断和优化 MAC 本身，并满足第 3.3 节的升级条件时，外部开发者才可以对生成项目做最小范围的只读检查；即使如此，也不得直接修改生成项目。

## 3. 两种工作模式

### 3.1 MAC 开发调试模式

目标是修复 MAC 本身。

允许：

- 阅读和修改 MAC 源码、Prompt、Schema、状态机与测试；
- 查看 MAC 日志、数据库、任务记录和通知记录；
- 分析 Agent 为什么违反合同、为什么重试、为什么路由错误；
- 运行 MAC 单元测试、集成测试和真实飞书流程测试；
- 重启 MAC 服务并验证运行状态。

限制：

- 修复必须针对通用根因；
- 不得为某一个用户措辞、某一个项目名或某一个错误文本增加硬编码；
- 不得只依赖文档提醒；自然语言边界必须由 `tests/test_architecture_boundaries.py` 的 AST 守卫持续检查；
- 不得通过修改生成项目来掩盖 MAC 的缺陷；
- 不得把通知静音当作修复失败机制。

### 3.2 外部黑盒验收模式

目标是模拟只有手机或正常产品入口的真实用户。

允许观察和提交的证据只有：

- 使用的入口和运行环境；
- 原始用户输入；
- 页面、飞书或 App 的可见输出；
- 交互次数、顺序和等待时间；
- 卡片、按钮和截图表现；
- 用户期望的可见行为。

禁止使用源码、内部日志、diff、测试产物或隐藏请求参数证明成功或失败。

MAC 内部的 Coder、Tester 和 Reviewer 仍可进行白盒工作，但内部证据不能替代外部黑盒验收。

### 3.3 从黑盒验收升级到 MAC 诊断

“尽量不看生成项目代码”是默认原则，不是禁止诊断 MAC 的绝对限制。当出现以下情况时，可以暂停当前黑盒回合，显式切换到 MAC 开发调试模式：

- MAC 的路由、上下文、Prompt、Agent 合同或状态流转明显不符合预期；
- 同类问题经过 MAC 内部 Agent 多次修复仍从真实入口复现；
- 仅凭手机端可见现象和 MAC 自身任务记录不足以判断 MAC 为什么没有正确驱动生成项目；
- 需要比较“MAC 提供给 Agent 的信息”和“Agent 实际落地的结果”，才能修复通用系统缺陷。

升级后的检查必须遵守最小必要原则：

1. 先记录黑盒入口、输入、可见结果和期望结果；
2. 明确说明已暂停黑盒验收并进入 MAC 诊断模式；
3. 优先检查 MAC 自身的 Prompt、任务输入、状态和日志；
4. 仍不足时，才只读检查与该问题直接相关的生成文档或代码；
5. 记录为什么必须查看、查看了哪些范围，以及发现的 MAC 层根因；
6. 只能修改 MAC，不能直接修改生成项目；
7. 修复必须泛化到同类问题并增加 MAC 回归测试；
8. 诊断所得的内部证据不得计入黑盒通过；修复后必须回到全新或隔离会话，从真实入口重新验证。

如果仅凭用户可见证据和 MAC 自身信息已经足够定位，则没有必要查看生成项目。

## 4. 权限边界

### 4.1 可以做的事

- 修改 MAC 系统本身；
- 通过飞书向 Coordinator 提交需求、回答问题和提供反馈；
- 通过真实网站、飞书或 App 操作生成项目；
- 将真实可见问题作为结构化反馈交给 MAC；
- 检查 MAC 是否正确保存事实、调度 Agent、重试和流转状态；
- 在 MAC 层定位并修复协议、路由、状态机、通知和运行时问题。
- 在第 3.3 节条件满足时，对生成项目做有记录、最小范围、只读的诊断，以定位 MAC 的通用缺陷。

### 4.2 不能做的事

- 直接实现或修复生成项目；
- 在黑盒验收仍进行时静默查看生成项目内部实现，或没有必要性时扩大检查范围；
- 替 Coordinator 完成参考项目调研并把答案灌给下游 Agent；
- 用内部测试通过代替真实入口通过；
- 将参考项目的技术依赖自动认定为目标项目需求；
- 遇到具体失败后只写一个匹配该 case 的特殊分支；
- 隐藏真实失败或在尚有阻塞时宣称完成。

### 4.3 必须做的事

- 先判断问题属于 MAC 还是生成项目；
- 属于 MAC 的问题必须在 MAC 层修复并补通用回归测试；
- 属于生成项目的问题必须通过 Coordinator 路由给内部 Agent；
- 每次修复后验证同类问题，而非只复测原句；
- 完整测试时保持黑盒边界，记录可复现的用户证据；
- 必须查看生成项目时先退出当前黑盒回合，并按第 3.3 节记录诊断边界；
- 外部依赖确实不可用时如实记录，不得伪造通过。

## 5. 问题归属规则

| 现象 | 归属 | 处理方式 |
|---|---|---|
| Coordinator 遗漏需求、重复提问或误解参考范围 | MAC | 修 Prompt、上下文或确定性 Policy，并补测试 |
| Agent 频繁输出无效 JSON、违反 Schema 或重复同类合同错误 | MAC | 修 Prompt、Schema、Runtime 反馈和重试策略 |
| 状态机卡死、重复卡片、审批失效或反馈没有传递 | MAC | 修 Orchestrator、Handler、状态机或通知层 |
| 自动重试过程在飞书持续刷“编码失败/测试失败” | MAC | 区分尝试失败、质量失败和最终失败，聚合通知 |
| 网站按钮无效、回复错误或记忆行为不符合合同 | 生成项目 | 提交黑盒反馈，由 Coordinator 路由给 Coder |
| Tester 发现代码级缺陷 | 生成项目 | Tester 创建结构化反馈并进入 REWORK |
| 目标合同未要求某外部集成，但 Agent 把它当作前置条件 | MAC | 修需求迁移和范围判断规则 |
| 目标合同明确要求的外部服务不可用 | 外部阻塞 | Coordinator 先尝试系统能力，无法解决时再询问用户 |

## 6. 失败语义

MAC 必须区分以下状态，不得统一显示为“编码失败”或“测试失败”：

1. **本次 Agent 调用无效**：Runtime、网络、解析或 Schema 错误，系统正在自动重试；
2. **Agent 合同未满足**：本次输出被拒绝，系统把精确原因交回同一 Agent 修正；
3. **阶段执行成功但质量未通过**：Tester/Reviewer 已完成工作，并给出 blocking feedback；
4. **自动重试成功**：前一次尝试已被后续成功尝试取代；
5. **重试耗尽后的最终失败**：系统无法继续，需要恢复动作或用户介入；
6. **正常 REWORK**：不是系统崩溃，而是质量流程要求返工。

飞书通知应展示当前有效结论。中间尝试可以更新同一进度卡或折叠为摘要，不能让已经恢复的临时失败永久表现为项目最终失败。

## 7. 标准执行流程

### 阶段 A：稳定 MAC

1. 从 MAC 任务记录归类失败；
2. 找到通用根因；
3. 修改 MAC；
4. 增加覆盖同类失败的测试；
5. 运行完整单元测试；
6. 重启服务并确认飞书连接和管理接口正常。

### 阶段 B：通过真实对话建立合同

1. 外部用户只通过飞书提出需求；
2. Coordinator 自行读取授权的参考项目；
3. Coordinator 区分产品能力、目标合同和参考承载方式；
4. 只有真正影响目标行为且无法合理推断的问题才询问用户；
5. 用户确认一次完整执行范围后启动状态机，不重复确认。

### 阶段 C：MAC 自主交付

1. Planner 形成需求、架构和实现规格；
2. Coder 实现并运行本阶段测试；
3. Tester 和 Reviewer 独立验证；
4. 阻塞问题形成结构化 FeedbackPacket；
5. Coordinator 将必要事实提供给对应 Agent；
6. 返工完成后重新验证，直到质量关通过。

外部开发者不得在此阶段直接接触生成项目实现。

### 阶段 D：完整黑盒验收

1. 使用全新用户或隔离会话；
2. 先按 `testing-taxonomy.md` 声明本轮是 T5 私聊 UI、T6 用户本人、T7 生成项目入口或 T8 内部主动验收；不同层级不得互相替代；
3. 从所声明的真实产品入口操作；
4. 按确认后的验收标准和行为探针逐项验证；
5. 记录输入、输出、次数、顺序和环境；
6. 失败时只提交可观察事实；
7. 由 MAC 自行定位、修复并给出新的黑盒复测合同；
8. 从相同层级的真实入口复测，不以代码、单测或另一个测试层级代替。

### 阶段 E：处理新发现的问题

- 生成项目问题：反馈给 MAC，继续状态机；
- MAC 问题：退出当前黑盒回合，优先用 MAC 自身信息诊断；必要时按第 3.3 节只读检查生成文档或代码，修复 MAC 并回归测试；
- 测试方法问题：修正测试隔离或前置条件，作废无效结论；
- 合同范围问题：回到 Coordinator 更新合同，不让 Coder 猜测。

## 8. 黑盒反馈格式

每个外部反馈至少包含：

```text
入口：用户从哪里操作
环境：设备、浏览器/App、是否为全新会话
输入：用户实际输入或点击内容
可见结果：用户实际看到的内容
次数与顺序：重复次数、消息或卡片顺序
期望结果：从用户角度应当看到什么
影响：该问题阻塞了哪条验收标准
```

不得在外部反馈中猜测源码根因。诸如“可能是某函数没有去重”只能由内部 Agent 调查后提出。

## 9. 完成标准

只有同时满足以下条件，才能宣称整个架构和测试完成：

- MAC 的 T1/T2/T3 自动化回归通过；
- T4 真实飞书传输流程覆盖确认、驳回、选择、澄清、返工和恢复；
- 涉及 Coordinator、自然语言问答、私聊上下文或用户已报告私聊失败时，T5 真实私聊界面自动黑盒通过；
- 飞书中没有被误标为最终失败的已恢复尝试；
- Coordinator 能正确区分目标能力和参考承载方式；
- 生成项目由 MAC 自主完成，没有外部直接改代码；
- 生成项目全部确认验收标准均有内部质量证据；
- 生成项目全部用户可见行为均从 T7 公开入口通过黑盒验证，系统可观察验收项同时有 T8 主动验收证据；
- 失败、跳过和外部阻塞均被如实记录；
- 服务重启恢复、审批幂等和消息去重符合预期。

测试脚本的 `passed`、HTTP 200、Schema 合法、代码存在或内部 Agent 声称成功，单独都不构成完整通过。

## 10. 当前需要完成的工作

按优先级继续处理：

1. 修复 MAC 对参考能力与参考承载方式的范围判断；
2. 修复 Agent 尝试失败、质量失败、REWORK 和最终失败的通知语义；
3. 减少可避免的 Schema、合同、worktree 和重试失败；
4. 让自动重试复用上下文，并在成功后收拢临时失败状态；
5. 为上述失败类别增加通用回归测试；
6. 完成 MAC T1-T4 回归，并按改动范围补充必须的 T5；
7. 从全新会话开始一次 T7 生成项目入口黑盒验收；
8. 黑盒过程中默认不读取生成项目代码；只有为诊断 MAC 且满足第 3.3 节条件时才做最小只读检查，始终禁止直接修改生成项目。

此前围绕 WeFlow 和微信登录得出的个人网站验收结论无效。除非后续目标合同明确要求真实微信集成，否则它们不再作为个人网站的实现或测试前置条件。

## 11. 决策原则

遇到不确定情况时，按以下顺序处理：

1. 先依据已确认合同和带时间的有效事实；
2. 再由 Coordinator 判断 MAC 是否已有能力解决；
3. 再询问相应内部 Agent；
4. 只有 Coordinator 无法回答且该问题会实质改变结果时，才询问用户；
5. 用户没有回答旧问题而提出新问题时，正常处理新问题并保留旧问题；
6. 不因追求自动化而扩大权限边界；
7. 不因测试成本较高而降低真实入口验收标准。

本章程是后续工作的约束。若执行方式与本章程冲突，应停止当前路径，先纠正 MAC 或测试方法，再继续推进。
